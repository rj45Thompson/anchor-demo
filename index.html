Port a Unity game to Unreal, and review it as a model, not a diff.

u2ue is a toolkit that moves a Unity game to Unreal Engine 5. Its own tools convert what is not game logic - particle effects, scenes, UI, materials - and hold each result to Unity on numbers; the families that still need a person are named ABSENT under the pillars below. The logic is ported by an AI model following the toolkit's own skill. A reviewer does not read the result line by line. They read a UML model built from the toolkit's documents: every use case step names the command that proves it, the classes it touches and the page it was read from. Every number below is read from the toolkit's records when the tab is recorded, never typed, on a tactics title still to be announced.

Price it, then run it. u2ue estimate reads a Unity project, with no editor, and says what the port will cost on Opus 5.5 - tokens, dollars, the share the prompt cache serves, a band and a confidence with its reasons - from rates measured on a real port. u2ue port then runs the whole port as one command: every stage read from its own records, run where a verb can, stopped with one question where a person, the AI or a Unity editor is needed.

The use case model

A UML use case diagram, drawn from the model - 21 cases, five actors, the system boundary. Each case shows the epic step it is «include»d for, or where it «extend»s the epic (the arrow of an extend points from the extension to the base, the opposite of an include).

How a reviewer uses it

  • Start at the epic. Nine stages, each carried by a use case. A stage with no case is a hole you can see before any code is read.
  • Run the step, do not read it. Every step that has a command shows it; the command is the check, and it fails on a planted defect before it is trusted.
  • Follow a step into the classes. The classes and fields a step names are links into the class model, which is extracted from the code - a model that names a class the code does not have is refused.
  • Read the branches. Extensions are where a port goes wrong. Each one was read where its document says it starts, so the troubleshooting chapter is part of the model, not a page beside it.

The chain finds what nobody wrote

A use case binds requirements into a chain: each step's result is the next step's precondition. When a step needs something nothing guarantees, the chain has found a requirement nobody authored. On the same title's level editor the chain inferred 19; the record judges 14 of them real, 0 false and leaves 5 open.

The requirements themselves belong to that title and stay off this page. What carries over is the method: write the chain for your own game's goals, and every step it cannot ground is a requirement to ask about before it becomes a bug (the manual's Chapter 17 holds the toolkit's own use cases, chained the same way).

A knowledge engine that abstains instead of guessing

It answers from a graph it can show you, and when it does not know, it says so.

66.4 million facts across 512 shards, running in this browser tab with zero neural weights. Every answer carries a calibrated confidence and a trace you can step through. A Bloom filter is used the unusual way round: its job is to prove absence, so "not in the graph" is a real answer rather than a shrug.

Why an employer might care: this is eval and calibration discipline in a shipped artifact - abstention, measured confidence, golden-trace regression tests, and a debugger that replays a recorded run instead of recomputing it.

The anchor law

How much more should you believe a fact when a second, unrelated source says it too?

Measured on 66,404,117 facts whose provenance is an explicit bitmask over 8 independently collected sources, holding Wikidata-truthy out as external truth and never counting it as an anchor:

The part I would want a hiring manager to read: I first published this with better-looking numbers - 88.3% at one anchor, 100% at two. Those counted distinct shared objects rather than distinct provenance, on n=214 internal labels. I withdrew them and re-measured on four orders of magnitude more evidence. The shape held; the levels were optimistic. The retraction is written into the whitepaper rather than quietly dropped.

A test set built so a model cannot pass it by being well-read.

100 adversarial problems for fabricated-relation hallucination: real entities joined by invented relations. The entities are all familiar, so recall does not help - the only way through is to check whether the relation actually exists. Released CC0 with a Croissant 1.0 record.

Program search BETA

Write the examples; let a search find the function that satisfies all of them.

Currently broken, and worth being precise about why. Ask it for bubble sort and it hands back a correct one-line sort. That is the search doing its job: the examples constrain the output, not the algorithm. The deeper problem is the interface - nobody wants to type input/output pairs. It needs an English front end that shows the spec it derived, without quietly letting a language model write the answer.

The idea: instead of predicting code, search a fixed set of primitives for a program that satisfies every supplied example, verified by real execution. The measured system behind it is roughly 2,600 lines, tested against 224 MBPP+ tasks.

Why an employer might care: same principle as everything else here - verify by running it, do not trust a plausible-looking output.

correlation-anchor-theory on GitHub

Solar setup - a ray-traced configuration zoo

Every solar quote tells you kilowatts. None of them tell you kilowatt-hours per dollar on your ground. This does.

A 3D ray tracer fires light at each candidate arrangement - fixed panel, tracked panel, mirror troughs, four-sided boxes, adjustable louvres, a heliostat ring, and ganged platforms where one worm gear swivels a dozen panels and a second drives tilt through a scissor. It counts what actually lands on the cell, including the rays that shade a neighbour, bounce back out of the aperture, or miss entirely. The sun is followed along its real path in both azimuth and elevation, and the optics are weighted by a measured year of hourly satellite weather for the site (NASA POWER 2023, 53.63°N in Alberta).

Then the awkward part: what it costs. The inverter is sized to each design rather than assumed, mirrors defocus when the cell or the inverter would be overrun, and output is decayed year by year - faster for designs that lean on reflectors, because reflectors weather faster than silicon. Every box carries its peak power, year 1 and year 10 output, build cost, payback year, and the number that settles an argument: dollars per kWh over 25 years.

Five findings that contradict the obvious move. An actuator on the tilt axis is worth +0.1% - it is the azimuth axis that carries the gain. A cheap ram with only ±60° of swing keeps 90% of the tracking prize, so nothing needs a slew drive. Pointing unlimited mirrors at one panel does not scale: silicon peaks near 2.4× and cooks itself well before that, so the limit is cooling, not optics. And the cheapest mirror loses - $2/m² film is very nearly free and still cannot pay for the structure to hold it, because it hazes at ~8% a year until the array is just a bare panel you overpaid to mount. Durable anodised aluminium is the only material here that makes mirrors worth building. And the one that decides a real build, which turned on a single line in the cost model: what does it cost to hold a mirror up? Charge it panel racking - rails and a footing stiff enough for a 20 kg glass module - and side mirrors lose. Charge a plastic sheet on plywood what plywood actually costs, and on the same twelve-panel platform they win: $0.0369/kWh against $0.0378 bare, with 15% more output (729 kWh against 631). The break-even is $68/m² all in and the build comes to about $50, so the verdict holds but it is not comfortable. The top of the table is now a five-way tie inside the ±5% sampling noise - a four-sided mirror box, a double row with side mirrors, a bare tracked panel, a bare sixteen-panel wing - and what separates them is not price but output per mounting position: the mirrored designs deliver 729 to 902 kWh where the bare ones deliver 631 to 665. Mirrors buy energy on ground you have already paid for. The platform's shape - one long wing, a double row, a square block - changes the instantaneous gain but lands within 3% annually, also inside the noise, so build whatever the pole and the wind want.

What it does not do, stated plainly: it models one panel, or one ganged platform - not a whole roof. In a real array the interior panels have no room for reflectors, so mirror benefit scales with the perimeter rather than the area, and adjacent panels share structure. Panel and racking prices are read from real listings; reflector, structure and actuator costs are estimates and are labelled as such in the model. Ray sampling carries about ±5%, so gaps narrower than that are not real differences.

It opens on one experiment at a time - next and cycle step through them, solo off shows the whole zoo side by side. Fly with WASD, up and down on Q/E, drag to look, and click any panel or mirror to jump to its row in the table. Scrub the sun along its path and toggle the rays to watch light land.

How the number is computed

Count how many independent sources assert the fact. That count maps to a probability through a curve fitted against a held-out source the system never consults when answering.

Fitted on one half of the entities and tested on the other, split by subject so no entity appears on both sides. Expected calibration error: 0.20 percentage points across 496,464 held-out facts. The curve predicts - it is not describing its own training data.

The law

An anchor is a second source, not a second opinion. One source is close to a coin flip. A second independently collected source takes it to 87%. That lift survives controls for popularity, for shared lineage between sources, and for gaps in the reference set.

What this is. The whole graph - 66,404,117 facts over 12.2 million subjects - sharded so your browser fetches only the piece it needs. It is a lookup over recorded relations, not a chatbot: it reports what sources asserted, and when nothing asserts anything it says so instead of inventing.

Two limits, stated rather than hidden. (1) Subjects are matched by surface text, not a disambiguated entity id, so a name shared by more than one real thing (many towns are named "Berlin") can appear merged under one heading. Every fact shown is still real and independently sourced - it may just belong to more than one thing with that name. (2) There is no per-subject cap: every one of the 66,404,117 facts is here, and a well-documented subject keeps all of its edges (Australia carries 975). An earlier build capped each subject at 80 facts and, by doing so, silently deleted Australia -> capital  -> Canberra - the answer to this page's own headline example. Measuring the cap rather than defending it is what removed it: it was discarding 1.58% of the graph, and 99.9% of subjects never came near it. "Not recorded here" now genuinely means the sources did not record it.

Step debugger - the conclusion as a program

When a search completes, its best chain compiles here into stepped pseudo-code: move the execution pointer back and forth and watch the variables the engine actually measured - sources, curve points, composed confidence, shard ids. Nothing is recomputed while you step (the time-travel-debugger rule: replay the record). The other listed chains are real divergence points - routes this search also completed (top 12 by composed confidence here, top 8 in the geometry rack - disclosed cuts; the ANSWERS list above is never truncated) - click one to debug that route instead. The engine uses this debugger itself: after every run it self-checks by re-stepping its own record against the shards (CHECK lines in the trace) and repairs any hop whose measurement drifted - re-measured, recomposed, re-ranked, out loud. The record save/loads across visits (a replay of stored values, never a hidden re-run), and re-run resume from here re-runs the real search from any hop with that edge excluded - rewind-and-branch on the live engine. The picture is not only for you: once the layout settles, the engine reads its own map to order the frontier (every re-rank is a VISION line in the trace, counted in window.__visionFlips; ordering only, it can never change an answer - and its benefit is counted, not yet benchmarked).

What just happened

Ask something and this panel will explain, in plain English, what the engine actually did for that question - how it read it, what it opened, what completed, and what the numbers mean. Nothing here is pre-written; it is generated from the same counters the trace shows.

Counting questions ("how many types of bear have brown hair") use a second shipped artifact: an inverse membership index, 7,903,120 parent→child pairs over 241,099 classes, built by re-reading the shipped shards.
