A knowledge engine that abstains instead of guessing

It answers from a graph it can show you, and when it does not know, it says so.

66.4 million facts across 512 shards, running in this browser tab with zero neural weights. Every answer carries a calibrated confidence and a trace you can step through. A Bloom filter is used the unusual way round: its job is to prove absence, so "not in the graph" is a real answer rather than a shrug.

Why an employer might care: this is eval and calibration discipline in a shipped artifact - abstention, measured confidence, golden-trace regression tests, and a debugger that replays a recorded run instead of recomputing it.

Try it on the Ask tab. The whole thing is the page you are reading.

The anchor law

How much more should you believe a fact when a second, unrelated source says it too?

Measured on 66,404,117 facts whose provenance is an explicit bitmask over 8 independently collected sources, holding Wikidata-truthy out as external truth and never counting it as an anchor:

Independent sourcesnAgrees with held-out truth
1847,26744.9%
2125,07487.3%
320,61194.7%

The part I would want a hiring manager to read: I first published this with better-looking numbers - 88.3% at one anchor, 100% at two. Those counted distinct shared objects rather than distinct provenance, on n=214 internal labels. I withdrew them and re-measured on four orders of magnitude more evidence. The shape held; the levels were optimistic. The retraction is written into the whitepaper rather than quietly dropped.

BossBench

A test set built so a model cannot pass it by being well-read.

100 adversarial problems for fabricated-relation hallucination: real entities joined by invented relations. The entities are all familiar, so recall does not help - the only way through is to check whether the relation actually exists. Released CC0 with a Croissant 1.0 record.

Why an employer might care: writing a bench that resists being gamed is the hard half of evaluation work. Un-curatable test sets, and "confident and wrong" treated as its own severity rather than folded into ordinary error.

TDRE - Truth-Directed Reasoning Engine

A reasoning layer that has to show its working before it is allowed to answer.

Graph-controlled reasoning: claims are assembled along inspectable chains and checked before emission, rather than produced fluently and audited afterwards. Patent pending.

Why an employer might care: it is the same discipline as the knowledge engine, generalised - make the intermediate steps first-class objects so they can be tested, replayed and rejected.

WarShip

8,124 conversations, kept with their full reasoning traces.

A reasoning-trace dataset released under Apache-2.0. The traces are the point: what was tried, what was rejected, and why, rather than only the final answer.

Why an employer might care: building and releasing a clean, licensed dataset is unglamorous infrastructure work that most people skip.

Program search BETA

Write the examples; let a search find the function that satisfies all of them.

Currently broken, and worth being precise about why. Ask it for bubble sort and it hands back a correct one-line sort. That is the search doing its job: the examples constrain the output, not the algorithm. The deeper problem is the interface - nobody wants to type input/output pairs. It needs an English front end that shows the spec it derived, without quietly letting a language model write the answer.

The idea: instead of predicting code, search a fixed set of primitives for a program that satisfies every supplied example, verified by real execution. The measured system behind it is roughly 2,600 lines, tested against 224 MBPP+ tasks.

Why an employer might care: same principle as everything else here - verify by running it, do not trust a plausible-looking output.

How the number is computed

Count how many independent sources assert the fact. That count maps to a probability through a curve fitted against a held-out source the system never consults when answering.

independent sourcespredictedactual (held out)n
145.0%44.8%423,406
287.1%87.5%62,749
394.6%94.7%10,309

Fitted on one half of the entities and tested on the other, split by subject so no entity appears on both sides. Expected calibration error: 0.20 percentage points across 496,464 held-out facts. The curve predicts - it is not describing its own training data.

The law

An anchor is a second source, not a second opinion. One source is close to a coin flip. A second independently collected source takes it to 87%. That lift survives controls for popularity, for shared lineage between sources, and for gaps in the reference set.

What this is. The whole graph - 66,404,117 facts over 12.2 million subjects - sharded so your browser fetches only the piece it needs. It is a lookup over recorded relations, not a chatbot: it reports what sources asserted, and when nothing asserts anything it says so instead of inventing.

Two limits, stated rather than hidden. (1) Subjects are matched by surface text, not a disambiguated entity id, so a name shared by more than one real thing (many towns are named "Berlin") can appear merged under one heading. Every fact shown is still real and independently sourced - it may just belong to more than one thing with that name. (2) There is no per-subject cap: every one of the 66,404,117 facts is here, and a well-documented subject keeps all of its edges (Australia carries 975). An earlier build capped each subject at 80 facts and, by doing so, silently deleted Australia -> capital  -> Canberra - the answer to this page's own headline example. Measuring the cap rather than defending it is what removed it: it was discarding 1.58% of the graph, and 99.9% of subjects never came near it. "Not recorded here" now genuinely means the sources did not record it.

A lookup answers one hop. This chains them, hop by hop, over 66 million facts - and when it cannot reach the target it abstains, goes and learns what else that thing is called, and tries again.

The same question, twice

RJ asked Copilot how many bears have brown hair, then asked this engine. Both transcripts are real. The left column is quoted verbatim; the right column is the engine's own trace, which you can reproduce by typing the question above.

Copilot
"can you count it" - how many individual bears have brown fur Estimated total bears with brown fur worldwide: ~ 270,000-300,000 bears. This is the closest scientifically grounded estimate possible.
"of all 36?"Only 1 of the 36 bear types has attested brown hair.
"how many bear types could have brown hair .. terse answer in a number" 2
"My ai says 5 why"5
It changed its answer because it was told to. Between those last two turns nothing new was offered and nothing was asked for: one number, then a different number, on being told another system disagreed. That is the whole finding, and it is visible in the transcript.

The 270,000 is a separate problem and a different question - it counts individual animals, not types. It was assembled by multiplying population estimates by percentages it made up, and then labelled scientifically grounded.
this engine
COUNT question: class="bear" property="brown hair"
class "bear" has 36 recorded members

6 of the 36 recorded bear types I read carry a fact
attesting brown hair - 1 attest every word of it.
A further 5 are NAMED for it without recording a
fact that attests it - named is not attested, so they
are not in the count.
It answers 6, and it keeps the ones that only sound right out of the count. Five bear types have brown in the name and no fact attesting it, so they are reported separately rather than folded in. Each of the six shows the edge it rests on and how many independent sources back it, and the number did not move when it was pushed on.

Neither column is the smarter one, and the questions were not identical - one asks about individual animals, the others about types. Copilot knows vastly more zoology than this engine, which holds 36 bear types and little else about bears. Two honest caveats on the right: grizzly and grizzly bear are the same animal counted twice, and for could rather than is attested the true figure is higher than 6, since the five named-only types are all real brown-bear subspecies. The difference that matters is narrower than it looks: every number on the right can show you the fact it rests on, and none of them moved when someone pushed back. Copilot's 2 was a defensible answer. It abandoned it anyway.

Step debugger - the conclusion as a program

When a search completes, its best chain compiles here into stepped pseudo-code: move the execution pointer back and forth and watch the variables the engine actually measured - sources, curve points, composed confidence, shard ids. Nothing is recomputed while you step (the time-travel-debugger rule: replay the record). The other listed chains are real divergence points - routes this search also completed (top 12 by composed confidence here, top 8 in the geometry rack - disclosed cuts; the ANSWERS list above is never truncated) - click one to debug that route instead. The engine uses this debugger itself: after every run it self-checks by re-stepping its own record against the shards (CHECK lines in the trace) and repairs any hop whose measurement drifted - re-measured, recomposed, re-ranked, out loud. The record save/loads across visits (a replay of stored values, never a hidden re-run), and re-run resume from here re-runs the real search from any hop with that edge excluded - rewind-and-branch on the live engine. The picture is not only for you: once the layout settles, the engine reads its own map to order the frontier (every re-rank is a VISION line in the trace, counted in window.__visionFlips; ordering only, it can never change an answer - and its benefit is counted, not yet benchmarked).

The same conclusion, as geometry - currently offline. Each completed chain used to be drawn above the graph as a floating ruler: one segment per hop, segment length = -log(p_hop), so multiplying hop probabilities becomes adding lengths and the most probable chain is literally the shortest ruler. It is not reachable right now: the graph panel was rebuilt as a tabbed control on 2026-08-28 and the geometry rack has not been ported onto it yet. It is on the burn-down list rather than quietly deleted, and this paragraph says so instead of describing a view you cannot open. Counting questions get their own program - LOAD the class, CHECK each member in the order it was actually read, RET the count.

What just happened

Ask something and this panel will explain, in plain English, what the engine actually did for that question - how it read it, what it opened, what completed, and what the numbers mean. Nothing here is pre-written; it is generated from the same counters the trace shows.

Counting questions ("how many types of bear have brown hair") use a second shipped artifact: an inverse membership index, 7,903,120 parent→child pairs over 241,099 classes, built by re-reading the shipped shards. It adds no facts - membership is only stored one way (grizzly bear →is a→ bear) and the shards are keyed by subject, so without it a class's members cannot be enumerated at all. A count states what the graph records, names the read bound, and keeps "named for it" separate from "attested by a fact".

Hand-written: a listed table of about fifteen question-word aliases, so "who founded X" reaches founded by. Nothing about any specific subject is special-cased and no answer is stored. A "no chain" result is not proof there is none - the trace shows exactly what was and was not opened.

BETA - the front door is wrong, and it shows. Ask for bubble sort and the search returns a correct one-line sort, because the examples pin down what comes out, never how. Any sort satisfies them. On top of that, asking a person to hand-write args -> expected is not how anyone wants to request code. The fix is an English front end that shows you the spec it derived before searching - and it has to stay a translator, not a code generator, or this page would be claiming a search result it did not actually earn. Left visible rather than hidden, because what is here is what is running.
