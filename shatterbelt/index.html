The rules

Points
Large rock 25, medium 60, small 120. Big hunter 250, small hunter 1,000.
Ships
Three to start, and one more every 15,000 points.
Hunters
The big one fires anywhere. The small one aims at you, and aims better as your score rises.
Hyperspace
You land anywhere, at rest, with no shield. One jump in eight fails.
Edges
Fly off one edge and you come back on the other. So do rocks and shots.

THE INTERVIEW QUESTIONWhat this answers

I was asked this in a job interview:

"Asteroids: a spaceship shoots; rocks come in large, medium and small and get smaller each hit. Design the classes and the main loop."The question, as it was put to me

This page is my answer, built. It is an original game in that genre, with its own rules and numbers. The design is below, read straight out of the code, and the tests that hold the code to it are below that.

HOW IT IS BUILTThe classes

All the rules live in one file, core.js, with no browser code in it. The same file runs the game on this page and the tests in Node.

  • Entity is anything that moves and can be hit: a position, a velocity, a facing, a spin, a radius and whether it is alive.
  • Ship, Bullet, Rock and Hunter are entities with their own rules. A rock knows its size, its points and the size its pieces will be. A hunter knows where to aim.
  • Pool makes a fixed number of objects when the game starts, so play never allocates. It also holds every add and every remove until flush(), so no loop ever sees its list change under it.
  • Field is the play area. Its edges wrap, so it also knows the shortest way from one point to another, through an edge when that is shorter. Collisions and aiming both use it.
  • Game owns everything and runs one fixed step at a time. FixedTimestep turns real time into those steps. Random is seeded and InputLog keeps one byte of input per step, so a whole game replays from the two.

Drawn by tools/class_diagram.js, which reads the class, field and method names out of core.js. A test fails if this picture and the code disagree. Arrows point from a class to the class it extends; a field's type names the class it holds.

The main loop

One step of the game, as it is written in Game.step():

step(input = 0) {
  this.events.length = 0;
  this.time += STEP;
  this.steps += 1;
  this.handleInput(input); // 1. input: steer, fire, hyperspace
  this.update(STEP);       // 2. update and integrate: move everything, run the timers
  this.wrapAll();          // 3. screen wrap
  this.collide();          // 4. collide: circle against circle; hits only mark things dead
  this.flush();            // 5. spawn and destroy: the only place the world's lists change
  return this.events;      // 6. events out, for the renderer and the sound
}
  1. Input steers the ship, fires and jumps. Hyperspace takes a fresh press, not a held key.
  2. Update and integrate moves everything by its velocity and runs the timers: shot lifetimes, waves, hunter arrivals, the respawn.
  3. Wrap brings anything that left one edge back in at the opposite one.
  4. Collide tests circle against circle, the short way round the field. A hit marks things dead at once, so a rock hit by two shots in one step breaks once, but nothing is removed yet.
  5. Spawn and destroy happen together in flush(), after every loop over the world has finished. A broken rock's two pieces join here, one size down, at its position, turned apart and a little faster.
  6. Events go out: what broke, what fired, what jumped. The renderer and the sound read them. The rules never do.

Around it, main.js runs the frame loop: real time goes into FixedTimestep, which calls step() at exactly 60 Hz however fast the screen draws, and the time left over is used only to draw smoothly between two steps.

Why it is shaped this way

  • Destroy later, never during a loop. Removing an item from a list while walking it skips the next item. That bug is real and easy to write, so the pool makes it impossible, and a test plants it to prove the tests notice.
  • A fixed step. The same input gives the same game on a 60 Hz laptop and a 144 Hz monitor, and physics never takes a huge step after a stall.
  • A seeded generator and an input log. A game is its seed plus one byte per step. Play a game and press "Watch the replay": the page plays it again from those two and checks it ends in exactly the same state.
  • Rules out, events in. The rules know nothing about three.js or sound. Drawing reads the state and the events, so the rules can be tested in Node, and a different renderer could be dropped in.
