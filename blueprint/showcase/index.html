Fixing Blueprint Friction

Start with the hello world, a Pong ball and paddle in 32 nodes, then a whole game, an asteroid shooter: both playing on their converted code, every node lighting up as it runs. Then the real thing: a Blueprint someone pasted online, badly written the way most are, turned into code, traced node by node to the use case and requirement it serves, and drawn as a 3D city. Each friction named in the design discussion The Blueprint Paradox is measured on it.

Three ideas, each shown below: closed loop requirements (sheets 4 and 5), human ergonomics (sheets 2 and 3) and observational understanding (sheet 0's replays here, values and valves on the battles of a game in production).

Left: as read. Right: the OO shape proposed for what the brainstorm found. It is a design, and nothing here rewrites the Blueprint.

  • the casting trap: 4 Cast To nodes test an actor's class before using it - an interface the cast class implements, holding the members the code reads through the cast; the code asks the interface instead of casting
  • the same statements written twice (SetLockOnTarget#s1:then, SetLockOnTarget#s9:else) - extract one method and call it from both places
  • 3 events fired like function calls (LockON, LockOnDone, SetLockOnTarget) - private methods of the class: called in order, can return a result, cannot be fired from outside
  • 2 functions run by a NAME in a string (DistanceToFrank, ToggleLockOn) - a delegate bound to the method itself: a rename is a compile error, and the reference shows in a search
  • ClosestTargetDistance written by 2 graphs - one owner: a private field behind a single method that changes it (and tells whoever must know)
  • LockedOn written by 4 graphs - one owner: a private field behind a single method that changes it (and tells whoever must know)
  • LockedOnTarget written by 3 graphs - one owner: a private field behind a single method that changes it (and tells whoever must know)
  • FrankBP carries 11 fields, 2 components and 11 methods that are all one behaviour - one component any Character can add (composition), named after the system: FrankBP keeps being a Character, the behaviour moves out of its graph
  • state polled by looping timers (DistanceToFrank, ToggleLockOn) - ask when needed instead of polling: compute the value where it is used, and update on the owner's own tick

Human ergonomics: each friction the discussion names, measured

The Spaghetti Wire Effect

The design discussion arguesText code reads top to bottom, but a Blueprint carries every value on a wire, so one variable used by several distant nodes sends wires across everything else.
In this Blueprintthe author's own layout: 200 wires (82 exec, 118 data) with 29 crossings between wires of one graph; the longest 1509 units (straight segments between node positions - the text carries no node sizes)
In the viewthe view lays the same graphs out from the code's structure: 148 wires drawn, 0 spanning 6 or more statements, 0 nodes moved between two layouts, longest 1011 px (layout gate PASS); a value read far away gets a getter beside its reader instead of a wire
ANSWERED (measured)

Scale and Zoom Blindness

The design discussion arguesA large graph forces a choice: zoom out until the nodes cannot be read, or zoom in to fix a detail and lose the flow around it.
In this Blueprintthe event graph spans 2736 x 2160 units of canvas; finding one node means panning it
In the viewfly to any of 99 statements by name or text, one command, typed or spoken; island titles carry the map from far away and node labels fade in as you come close; 'ask' hands back only the slice that answers (results/RAG-LOCKON.md:16 At budget 3000 (the smallest that answers all 10): RAG 9053 tokens against CODE 246150 and RAW 1642300 - 27.2x fewer than the converted code, 181x fewer than the raw text.)
ANSWERED (measured)

Execution vs. Data Clutter

The design discussion arguesTwo kinds of wire share one canvas, exec wires that order events and data wires that carry values, and where they cross the logic is hard to follow.
In this Blueprint17 of those crossings are an exec wire over a data wire
In the viewin 3D the two never share a plane: exec pipes run above the nodes (lowest point y=0.466), data pipes below them (highest point y=0.125) - a 0.34-unit gap, so no exec pipe can cross a data pipe (view3d.js buildIsland)
ANSWERED (by construction)

The Hiding of the Hierarchy

The design discussion arguesA child Blueprint inherits everything from its parent yet opens on an empty graph, and the parent's logic is reached only through an explicit call node.
In this Blueprintthe pasted text names no parent class for either Blueprint
In the vieweach class is a district standing over its engine parent's floor, the parent READ from what the class uses on itself: Master_Enemy : Actor; FrankBP : Character (oo.js, the engine headers that declare those members)
ANSWERED (read, not drawn by hand)

The Lack of Encapsulation

The design discussion arguesText code hides a long chain of logic behind one method call; Blueprints tend to copy the whole chain into every graph that needs it, erasing the class boundary.
In this Blueprint1 rule written twice (SetLockOnTarget#s1:then), 3 events fired like functions, 3 members written by several graphs
In the viewassembled as classes (typed fields, methods, components), and each pattern named with the OO form that removes it: 9 proposals, each tied to the questions that found it (CLASSES.md)
ANSWERED for reading and planning; the view does not rewrite the Blueprint

The Casting Trap

The design discussion arguesPolymorphism lets code treat a child as its parent, but Blueprints lean on explicit Cast To nodes, so what should be one interface call becomes a roadblock in the graph.
In this Blueprint4 Cast To nodes test an actor's class before every use
In the viewthe proposed shape replaces them with an interface the cast class implements, holding exactly the members the code reads through the cast (LockOnInterface: float Distance_to_Frank_Var { get; }, bool IsDead { get; }, void LockOnInterface(Master_Enemy Locked_On_Target))
PROPOSED (a design, not a change)

The Multi-Dimensional Grid Problem

The design discussion arguesText stays compact through nested names; drawn as nested boxes, the same structure becomes a map to pan and zoom through just to find one variable.
In this Blueprintthe logic sits in 12 graphs across 4 pasted texts; a member like LockedOn is written in 4 of them
In the viewone command reaches any of them; the members panel lists every field with who writes and names it; the retrieval layer answers a question from the trace without opening a file (results/RAG-LOCKON.md:16 At budget 3000 (the smallest that answers all 10): RAG 9053 tokens against CODE 246150 and RAW 1642300 - 27.2x fewer than the converted code, 181x fewer than the raw text.)
ANSWERED (measured)

Invisible Relationships

The design discussion arguesText keeps relationships such as inheritance abstract; drawing each one as a pipe back to its parent would bury the graph in lines.
In this Blueprint5 calls are made by a function NAME in a string (DistanceToFrank, ToggleLockOn) - no reference the editor can find
In the viewevery call between graphs is an arc; a call by name marches in orange and says so; the interface is a ring the 6 messages go through; the parent is a floor, not a pipe per member
ANSWERED (drawn from the trace)

Encapsulation Gates

The design discussion arguesA strictly object-oriented graph would turn reading one value into a chain of reference, getter and access nodes, filling the screen with boilerplate.
In this Blueprint43 of 162 Blueprint nodes are variable reads and pure math - boilerplate a strict OO graph would multiply
In the viewthey are written INTO the statement that reads them (as the engine compiles a pure node in front of its reader), so a getter is a word in a line, not a node to wire
ANSWERED (measured)

The "Icing" Concept

The design discussion arguesThe visual layer is icing over the real code, but load-bearing icing: people remember where things are, so a generated map aids pattern finding and debugging.

In the viewthe visual map is generated from the code and never edited apart from it: every one of the 162 nodes becomes a graph node and maps to a requirement (S-BP spaces, 162/162), and the city is laid out from the code's structure, so it stays where the reader remembers it (0 nodes moved between two layouts)

Data as Flowing Water

The design discussion arguesThe graph could show execution as pulses and data as flow, a pipe's thickness for its type's weight and a swollen red pipe where the code bottlenecks.
In this BlueprintDistanceToFrank runs 100 times a second (OnComponentBeginOverlap(LockOnSphere)#s3); ToggleLockOn runs 100 times a second (SetLockOnTarget#s14) - nothing in the editor shows that cost

Time-Travel Auto-Replay

The design discussion arguesIf the engine kept a rolling record of execution, a failure could be replayed and scrubbed to the moment the data went wrong instead of guessed at.
In this Blueprintthe editor shows a value only at a breakpoint, live, one at a time

Coding via Observation

The design discussion arguesSeeing values flow invites changing them in place: a value adjusted on a wire, and the running game answering at once.
In this Blueprintchanging a value means editing, compiling and playing again

SHEET 5

Closed loop requirements: the loop an AI acts on

The design rule: closed-loop requirements replace the code as what an AI acts on, so it works from the loop rather than from prompts, and no mistake gets through unless the requirements carry it too. The node was judged by one question: what mistake can still get past it? Thirteen criteria answer it, each named by the mistake it stops, and 6 of them could not be held at all before today. Three additions to the node made all 13 measurable. The effect says, in the code's own terms, what each requirement makes the code set, call, branch on or read, and where. The terms bind each word of the requirements to the code names it means. The lock records each requirement's fingerprint as last verified.

A graph network as a suggester

Message passing over the graph proposes the step a statement belongs to: 86.9% right, against 73.7% for the nearest-cite baseline, and 99.0% against 97.0% for the use case. It is kept as a suggester. It never decides coverage.

Unreal's editor, panel by panel

The engine names 15 Blueprint-editor panels. 9 have an answer here. The rest are absent, each for a reason:
  • Class Defaults (DefaultEditorID): a clipboard copy carries no defaults (the sample's MaxDistance is read, never valued); an export does - whether to show them is an open product decision (IR-17)
  • Palette (PaletteID): no node is placed by hand: a change is a typed command on the code, through three gates (tools/edit.py, P6a, ED-2)
  • Viewport (SCSViewportID): the components' meshes and transforms live in the Blueprint asset, not in the graphs a person pastes - drawing them in place is an open product decision (IR-18)
  • Replace References (ReplaceNodeReferencesID): the view does not edit Blueprints; a rename goes through the C#, where the compiler finds every reference - and a call by NAME is flagged (Q-NAME), the one kind the engine cannot find
  • Timeline editor (TimelineEditorID): a Timeline has no code form: the converter keeps it as a marked island (BC-9); there are no curves to edit
  • User Defined Structure (UserDefinedStructureID): a struct's definition is an asset of its own, not a graph; structs reach the view as Make/Break nodes (BC-6)

SHEET 9

Not done, and why

  • No person has used the view yet, so how much friction it removes for people is unmeasured. Who tests it, against what, is IR-12.
  • This sample cannot be replayed with values: its enemy class and the engine's timers are not in the pastes, and every value would be invented. Every one of its paths replays instead, and value replays run on the battles of a game in production.
  • Speaking a change is not built. Under the closed loop a change belongs on a requirement's effect, and the loop then names the code that must change and what went stale. The page cannot write the model, so a spoken edit needs a local writer the toolkit does not have yet, and building one is an open product decision. Spoken commands work, where the browser offers speech.
  • Class Defaults and the components Viewport are open product decisions (IR-17, IR-18). A clipboard copy never carries defaults.
  • The OO shape is a proposal. Writing Unreal paste text back is not built: the engine's writer is C++, and the view holds no pin ids to write.
  • A second model's reasoning was not checked here, because the local model's server was down. The checker takes any model's chain in the same format.
