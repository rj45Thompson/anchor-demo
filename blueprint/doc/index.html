Closed Loop Requirements and the Blueprint View

RJ Thompson · 28 October 2026 · a draft prototype, built and measured by tools, not yet tested by people

Closed loop requirements turn a finished program into a complete, gap-checked set of requirements. Once every question is answered or handed to its owner, code, Blueprints and pictures are all views of one source. This document explains the idea, the three Blueprint friction points, and what the Blueprint view prototype has built and measured so far.

At a glance

Code or a Blueprint goes in; the loop holds it as one logic graph tied to requirements; every view people read is printed from that, never edited apart from it.

Closed loop requirements

Closed loop requirements are every problem, solution and interaction a program carries, aimed at being complete enough for an AI to rebuild the program exactly, with nothing misread. No rebuild from requirements has been tried yet; what is measured is that each requirement's effect can be checked against the code. They are reached from a finished product, not imagined up front.

  1. Start from finished code. Source that already does everything its users need.
  2. Read every line into a node graph. The prototype's reader is U2ue.CodeGraph, built on Roslyn, so it reads meaning and not only text.
  3. Tie each node to a use case step. Use case descriptions are linear: a main path plus every alternate path, each with its stated outcome.
  4. Walk the chain. A node, path or source sentence with no requirement becomes a typed question. It is never filled with a plausible guess.
  5. Close the loop. The loop is closed when every question is answered or handed to its owner.

Why it is the new raw element. Strip the syntax off a program and three things are left: problems, solutions and the interactions between a person and the system. We write them as user stories, use case descriptions and class diagrams of the concepts (not necessarily the code's exact classes). Everything above that layer, C#, C++ or a Blueprint, becomes an interpreted form, picked for whoever is reading.

The compiler for requirements. Code has a compiler and requirements never had one, so nothing said a branch was missed. The gap checker fills that role:

  • usecase_model.py checks the model as data with 17 rules, each shown able to fail by a planted fault.
  • usecase_kg.py holds the model as a SQLite knowledge graph and counts the independent evidence behind each requirement.
  • interrogate.py turns every hole in the chain into a question and exits non-zero while any is unanswered.

Measured on a public Blueprint. Each requirement is judged by what mistake can still get past it: 13 criteria. The requirement node as it stood could not hold 6 of them, so it gained three fields: an effect (what the code sets, calls, branches on or reads, and where), terms (words bound to names in the code) and a lock (fingerprints as last verified).

  • 35 of 43 requirements carry a check (an effect that can fail); the other 8 carry a written reason instead, calls only the author can make. The 84 checks from the 25 requirements read from the code all hold; since they are checked against that same code, they guard against change rather than prove it correct.
  • 13 checks from 10 of the owner's questions fail on the code as pasted: these are the defects the loop found.
  • 97 of 97 planted faults flip the result.
  • On a copy of the sample, an edited requirement and a changed statement it reads both came back stale.
  • The loop is still open: 43 holes from 18 questions only the author can answer. 11 requirements rest on the code alone, so a mistake already in the code is in them too.

A hello world first. Pong, two public Blueprints with 32 nodes between them, went through the same tools: 6 use cases, 10 requirements, 12 of 12 paths, 13 of 13 effects hold and flip. Its loop is open too, on 3 questions for its owner: the score, the two speeds, and which end a serve goes to.

A whole game. siljaZ's asteroid shooter (Unreal Engine 5.0, January 2023) is the one whole asteroid game on blueprintue.com; no classic Asteroids is pasted there. 16 of its 23 pastes, 232 nodes, convert to 83 statements in 20 graphs. The model holds 12 use cases and 24 requirements read from the nodes, and all 65 of their effects hold on the code and flip when a fault is planted. All 232 nodes are tied to a requirement, 37 of 38 outcomes are cited (1 excluded with its reason) and 53 of 64 paths are covered (11 excluded). Its loop is open on 15 questions only the author can answer, with 0 holes of ours.

One source, many views

Human ergonomics

Human ergonomics means breaking a hard problem into analogies and mnemonics a person already knows, arranged as parent and child, and read in a line. It is the shape layer: the same graph, laid out for a human mind rather than for the machine.

  • Analogies. A class is a district in a city; its parent class is the floor it stands on. Inheritance becomes a place you can see, not a fact you have to remember.
  • Parent and child. A large idea breaks into smaller ones you open one at a time. Use cases follow the same rule: epics hold user goals, and user goals hold subfunctions.
  • Linear. Steps read in order, like a story. Order pipes run above the nodes and value pipes below them, so the two never cross.
  • Stable places. Unchanged code lays out in the same place every time (0 nodes moved between two layouts), so spatial memory keeps working.

On the game's core, a one-to-one drawing would have 2,343 wires running six or more statements. The view draws 0: a value read far from where it was set gets a small Get chip beside its reader instead.

Two layout targets failed and are left as design calls, not patched: graphs average 2.5 nodes per line of code against an aim of 1.5, and big graphs open with every node showing against an aim of at most 30.

Observational understanding

Observational understanding means learning a system by watching it run, the way you learn plumbing by opening and closing valves. The system keeps running in front of you; you can see it, rewind it and change it mid-flight.

What you do What the view does Measured
Watch it run Pulses travel the order pipes; value pipes are as thick as their type is heavy; a hot path glows red In the public Blueprint, DistanceToFrank and ToggleLockOn each run 100 times a second, read from their timers
Rewind it Every path replays step by step and can be scrubbed back and forth; each step names its use case step and requirement 54 of 54 paths in the public Blueprint. On the game, a crit multiplier planted in a copy (1 to 1.1) made 4 of 6 battles diverge at a named step (339 to 372 damage)
Change it mid-flight A valve changes a value at a probe and replays every recorded battle, with no rebuild Doubling one damage value doubled every battle's first hit (503 to 1,006); the slowest whole replay took 0.84 s against a 2 s target

The valves run on headless replays of recorded battles, never on a live editor.

Try it: Pong plays live. What moves the ball is the converter's own graph of the Pong Blueprint, run statement by statement: each node glows in the city as it runs, Unreal 2D rings the nodes it came from, and the panel names the statement that just ran and the requirement it serves. The court around it (sizes, the speed, keys, the computer player) is authored, and the page lists every authored value. Run headless for 120 s, it made 52 paddle hits, each sent back, 19 wall turns and 17 goals, and all 13 converted statements ran. With the paddle's turn removed from a copy of the paste, the ball goes straight through (77 hits, 0 sent back).

What the loop caught on a public Blueprint

The requirement graph holds 18 questions only the Blueprint's owner can answer; an AI reasoning from the converted code alone reached 9 of them. Every one of the 162 nodes is tied to a requirement and all 54 paths are accounted for (48 covered, 6 excluded with a reason).

Some of what it flagged, each tied to the requirement that found it:

  • Two variables that never meet. The enemy writes DistanceToFrankVar; the search reads Distance to Frank Var.
  • A lock that never lets go. When the locked target dies, the lock is not released.
  • Hidden cost. Every enemy line-traces 100 times a second with debug drawing left on.
  • An unanswered handover. Nothing in the pasted graphs tells the old target it is no longer the target.
  • Calls a rename would break. Functions run by a timer are called by a name in a string, so a rename is not caught.

Status and open decisions

The prototype is built and machine-measured, and kept apart from the game it reads: it never writes the game's code or touches a live Unity or Unreal editor.

Built and measured: both converters, the five-way graph view, the 3D city (Three.js on WebGPU), two games playing on their converted Blueprints, replay and scrub, valves, the RAG layer (27.2 times fewer tokens than the converted code, 181 times fewer than the raw paste, all 10 test questions answered), the u2ue blueprint command, and two task rounds run by Claude (round 2: 32 of 32).

Looked at, not only measured. A city of nine classes once stood in a single row 631 units long and drew black beyond the fog, while the audit was green with 0 errors. Only looking at the screenshot caught it. Districts now wrap into rows. That is why every view here is both measured and looked at.

Not built or not verified:

  • No person has used the view. Friction removed for people is unmeasured.
  • Speaking a change (not just a command) and editing directly on the graph.
  • The Unreal editor version of the view.

Open decisions: who tests the view and against what baseline; browser first or a panel inside the Unreal editor; what the Class Defaults and Viewport panels map to; whether big graphs open folded; and whether the view joins the u2ue toolkit as a product.
