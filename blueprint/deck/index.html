How we build Blueprints this big in a day

We don’t draw Blueprints. We print them.

Someone wired Lock-On by hand, node by node: 162 nodes. Overnight we printed a whole game in production: 4,201 graphs, 67,284 nodes, 79,507 wires.

1

Read. Roslyn, the C# compiler’s own reader, takes in every line of the finished code: its meaning, not just its text.

2

Graph. Each method becomes one logic graph, and a call opens its own graph: 14,499 links, none to nowhere.

3

Print, then prove. The Blueprint is printed from the graph, and the graph prints back to the exact same code: 4,201 of 4,201.

Then the requirements hang on that same graph.

■ Lock-On, wired by hand: 1 square

The game, printed: over 415 Lock-Ons’ worth of nodes.

Counts: the Blueprint view’s build log, Wed 28 Oct (runs/graphs_build_tr2.log, REQ-BPV-7); Lock-On from FRICTION_LOCKON.md.

So how do you get Blueprints this big in a day? You stop drawing them. Somebody built Lock-On the normal way, dragging and wiring one node at a time: a hundred and sixty-two nodes. That same night we printed an entire game in production as Blueprint-style graphs: forty-two hundred graphs, sixty-seven thousand nodes, seventy-nine and a half thousand wires. That's more than four hundred Lock-Ons. Three steps. Read: Roslyn, the compiler's own reader, takes in the finished code by meaning, not text. Graph: every method becomes one logic graph, and calls link to each other's graphs. Print, then prove: the picture is printed from the graph, and the graph prints back to the exact same code, every one of the forty-two hundred. Nobody wires anything. And once the logic is a graph, the requirements can hang on it. That's the closed loop.

The big idea

Code is just one way
of writing it down.

Underneath every program is something rawer: the problems it solves, the answers it gives, and every exchange between a person and the machine. Capture all of it, with nothing left out, and code becomes a translation you pick, like a language.

That complete capture is what we call closed loop requirements.

This is the whole pitch in one sentence. Today the code is the only complete description of a program, so everyone has to read code. If the requirements are complete, they become the description, and every language, every picture, is just a view of them.

Closed loop requirements

How to easily understand closed loop requirements

Think of a recipe so complete that a stranger cooks your exact dish, and every “what if” is written down: out of eggs? oven runs hot? Nothing is left to guess.

1

3

Step by step, every side path too.

4

Every gap is a question

Asked out loud, never guessed.

5

The loop closes

Every question answered, or handed to its owner.

The easiest way in is a recipe. A normal recipe gets you close. A closed loop recipe is so complete that a stranger cooks exactly your dish, because every what-if is already written down. Closed loop requirements are that recipe for a program. Take a program that already works. Tie every line of its code to a step in a story, a use case: who does what, and why. Read the story in order, including every side path. Wherever a line has no story or a story has no line, that gap becomes a question, asked out loud, never guessed. Go round again until every question is answered or handed to the person who owns it. The aim is a recipe complete enough to rebuild the program exactly; that rebuild has not been tried yet, but every requirement's check can already be run against the code.

This is what makes the loop more than a list. Every requirement is judged by what mistake could still get past it, thirteen criteria in all. A requirement now carries its effect in the code's own terms, which is a check that can fail, plus the words it uses bound to real names in the code, and a lock that flags it stale the moment the requirement or the code it reads changes. On the public lock-on Blueprint, 35 of 43 requirements carry a check; the other 8 carry a written reason, because only the author can decide them. The 84 checks from the 25 requirements read from the code all hold; since they are checked against that same code, they guard against change rather than prove it right. The 13 checks from 10 of the owner's questions fail on the code as published, and those are the defects. All 97 planted faults are caught. A check, not a proof. Be honest about the finish line: the loop is still open, because 18 questions can only be answered by the Blueprint's author. And 11 requirements rest on the code alone, so a mistake already in the code would be in them too.

Keep in mind who reads these requirements: AI. Nobody types build GTA 6 into a chat box and gets GTA 6, because a prompt is a wish. It leaves every real decision open, and the AI fills each gap with a guess. Closed loop requirements are the opposite: every step of every story, every what-if answered or handed to the person who owns it, and a check the AI's work must pass wherever one can be written. The AI does not act on the prompt. It acts on the loop.

The visual clutter of Blueprints

The spaghetti wire effect

Text reads top to bottom. A Blueprint drags each value across the screen, so one shared variable cuts through everything else.

White wires say what happens next. Coloured wires carry values. They cross, and you have to track both at once.

Friction 2 · The objects go missing

Objects underneath, procedures on screen

The hierarchy hides

A child Blueprint inherits everything from its parent, yet its graph opens blank. Reaching the parent takes a special node.

No encapsulation

Text code hides a fifteen-step routine behind one line, TakeDamage(10). In Blueprints it gets copy-pasted, node for node.

The Cast To trap

Instead of one clean interface call, every use starts with a Cast To roadblock in the middle of the graph.

Blueprints are object-oriented. Every Blueprint has a parent class and inherits its health, movement and functions. But the graph hides all of it. In the lock-on sample, the pasted Blueprints never say what their parents are, there are four Cast To nodes standing in for what should be one interface, and the same six-node chain is copy-pasted twice.

Friction 3 · Forcing objects in is worse

Why a pure object graph fails people

The grid problem

Player.Weapon.Stats.Damage is one line of text. Drawn as boxes inside boxes, it is a map you have to travel.

Invisible relationships

Draw every child-to-parent link as a pipe and the screen turns into a matrix of lines.

Encapsulation gates

Showing Health on screen would take a reference, a getter and a gate, each one a node to wire by hand.

The obvious fix, draw the real object structure, makes things worse. Text hides nesting and relationships in a few characters; a picture has to draw them. In the sample, the logic is spread over twelve graphs, five calls are made by a name typed into a string so nothing can follow them, and more than a quarter of the nodes are just reading a variable or doing arithmetic. So the answer is not more drawing. It is a different shape.

What is easy?

Visual programming misread what makes things easy

The bet

Pictures are easier than words

So draw the code: boxes and wires instead of text. It works, for three nodes.

How people understand

We see pictures. We understand stories.

Who wants what, what happens next, and what if it goes wrong.

A wiring diagram is a picture with no story. That is why it stops being easy.

Visual programming is a textbook example of misunderstanding how people understand. It asked: what is easy? And it answered: pictures. That is half right. We take in a picture at a glance, and we remember where things are. But we understand through stories: someone wants something, things happen in order, and something can go wrong. A wiring diagram has the picture and none of the story, so it is easy on day one and impossible by month six.

Back to the cave

We have understood in stories since the cave

A use case is that same story: an actor, a goal, steps in order, and every “what if”. That is why the loop is built on them.

Long before writing, people passed on what they knew as stories, and painted them on cave walls: who, what they wanted, what happened, what to do when it goes wrong. A UML use case description is exactly that shape. Here is the hunt from the wall written as one: an actor, a goal, three steps in order, and the alternate path when the herd stampedes. That is why closed loop requirements are built on use cases, and why human ergonomics means stories in a line, not wires on a grid.

Human ergonomics means we take a hard problem and break it into analogies and mnemonics a person already understands, arranged as parents and children, and put in a line. In the view, a class is a district in a city standing on its parent's floor, so inheritance is something you see, not something you remember. Order runs on pipes above the nodes and values run below, so they can never cross. A value read far away gets a small chip beside its reader instead of a long wire: across the whole game core that is zero long wires, where drawing it one to one would have given 2,343.

Learn it by watching it run

Watch it run

Like water in pipes with valves. The system keeps running in front of you. How it was built. Five AI skills, each a plain-text playbook the agents load before they start. usecase-map writes the use cases from the problem story and keeps them apart from the code. usecase-interrogate is the gap checker that turns every hole into a question. morph maps every design option so nothing is left to chance. decide routes judgement calls through a calibrated matrix. autonomous-worker keeps the long build on a task list until it is done, with evidence.
