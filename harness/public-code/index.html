On code you can read for yourself

Three trials on 30 October 2026, on code outside our own project: two parts of Unreal Engine's own C# and the scoring rules of a shipped open-source game. Every number below was measured on these runs, and every defect was reproduced by running it. No test and no product code was written for any target: only the requirements model, and /// CHECKS: comments in a scratch copy of the tests. Findings were proven with throwaway calls that are not part of any result.

What was tested

  • Unreal Engine 5.7, EpicGames.Core/SemVer.cs. Requirements: the public Semantic Versioning 2.0.0 spec, every numbered rule either mapped or excluded with a reason. Tests: EpicGames.Core.Tests, 2 of them on this class.
  • Unreal Engine 5.7, EpicGames.Core/JsonObject.cs. Requirements: the class's own doc comments, Microsoft's published Equals and GetHashCode contract, and RFC 8259. Tests: 43 on this class. 37 C# files under the engine's Source/Programs name this class.
  • osu!, a shipped rhythm game (ppy/osu, MIT, commit 845336e), ScoreProcessor.cs and HitResult.cs. Requirements: their own doc comments. Tests: the 151 test cases in osu.Game.Tests/Rulesets/Scoring. The project has many more, which this pass did not run per break: see below.

Unreal's source is available to anyone with an Unreal licence, not to the general public, so this file gives counts, method names and calls we wrote, and no engine code.

The numbers

"Live" leaves out breaks that did not compile and breaks whose compiled code was proven identical to the original.

SemVer - Coverage tool, for comparison: 90% of lines, 85% of branches. - 246 breaks made; 236 live; 206 caught (87.3%); 30 got past every test. - 14 of those 30 sit on lines the coverage tool marks as covered. - 48 of 68 statements held by a test; 18 have a break that gets past. - 7 of the 16 requirements taken from the spec have no test about them, including every rule about which strings are valid. Which test is about what was our reading of each test, written before any break ran.

JsonObject - Coverage tool: 77% of lines, 69% of branches. - 582 breaks made; 429 live; 299 caught (69.7%); 130 got past every test. - 67 of those 130 sit on lines the coverage tool marks as covered. - 176 of 289 statements held by a test; 82 have a break that gets past. - 6 questions only the class's owner can answer.

osu! scoring - Coverage tool, from those 151 tests: 72% of lines, 78% of branches. - 563 breaks made; 536 live; 286 caught (53.4%); 250 got past those 151 tests. - 145 of those 250 sit on lines the coverage tool marks as covered. - 81 of 191 statements held by those tests; 110 have a break that gets past. - Read 53.4% as what those three test files hold, and as low for the game as a whole. We applied 7 of the surviving breaks by hand and ran the rest of osu.Game.Tests: TestFailScore, TestResetFromReplayFrame and AccuracyRankAndTotalScoreOfLazerScorePreserved catch some of them. We could not finish that project on this machine: its test host crashed on the clean copy and the broken one, at different points, with and without the visual tests, so what the rest of it would catch is unknown. - This pass ran before property bodies were walked, so 5 statements in property bodies got no break.

Checking the tool's verdicts without the tool

We applied breaks the tool said no test notices, by hand, to clean copies, and ran the tests ourselves.

  • SemVer: 6 breaks at once (including CompareTo always answering "equal" and TryParse no longer testing the match): all 90 tests that run still pass, 1 is skipped. No other test project names the class.
  • JsonObject: 8 breaks, each alone, against both test projects that name the class. 7 pass everywhere: RemoveField removes nothing, Equals answers true for anything, GetHashCode is always zero, the file reader stops skipping a byte order mark, the file reader stops skipping comments, Parse refuses trailing commas, a missing double field answers true.
  • The 8th is the tests' credit. JSON false reading as true passes the class's own project, but UnrealBuildTool.Tests catches it. We had first read that as uncaught, and running the second project corrected us.
  • 8 of UnrealBuildTool.Tests' 116 tests fail on the clean copy in our setup, so they could catch nothing here.

What it found

Each of these fails when run, on the code as shipped.

SemVer against the spec - Compare throws ArgumentOutOfRangeException on valid versions, including the spec's own example compared with itself: v = SemVer.Parse("1.0.0-x-y-z.--"); v.CompareTo(v);. Any pre-release ending in a hyphen does the same. - A hyphen is treated as a separator, but the spec separates identifiers only at dots. 1.0.0-alpha-10 sorts above 1.0.0-alpha-9 (the spec says below). 1.0.0-2 sorts above 1.0.0-1-2 (below). - 1.0.0-a.b and 1.0.0-a-b compare as equal while Equals says they differ. - It accepts strings the spec rules out: "1.0.0\n", and non-ASCII digits such as an Arabic-Indic zero in 1٠.0.0. Both come from .NET's meaning of $ and \d in the spec's regular expression. - Reach: no other C# file under the install's Source/Programs or Plugins names this class, so nothing in that tree is hurt today.

JsonObject against Microsoft's contract - Equals throws NullReferenceException on any object with a null field, even x.Equals(x). The contract says it must not throw, and that x.Equals(x) is true. - Two objects that compare equal have different hash codes, which the contract forbids. A HashSet of two equal objects holds 2. We found no HashSet<JsonObject> or Dictionary<JsonObject, ...> in the engine's C#.

osu! against its doc comments - TotalScoreWithoutMods reads 1,000,000 right after ApplyBeatmap, while TotalScore reads 0, and PopulateScore before the first hit copies that 1,000,000 into the score. The field's doc says "The total number of points awarded for the score without including mod multipliers", and Reset's doc says "Resets this ScoreProcessor to a default state", but Reset never clears it. We did not trace what the game does with the value afterwards. - After a second ApplyBeatmap on one processor, MinimumAccuracy reads 1 before any hit. We did not check whether the game ever applies a beatmap twice.

JsonObject: the owner's questions, not defects we can call - Equals answers false for two parses of the same text when it holds an array or an object. - A repeated name keeps the last value at the top level and throws one level down. {"A":1,"a":2} silently keeps one field, and throws one level down. RFC 8259 only says duplicates are unpredictable between programs. - Read accepts comments and Parse refuses them. A root that is not an object throws InvalidOperationException from Read and JsonException from Parse. - {"a":1e999} parses, then ToJsonString throws. {"id":9007199254740993} writes back as ...992, which RFC 8259 allows. - TryGetIntegerField accepts the string "12". TryGetEnumField<DayOfWeek> accepts "99". On a German machine TryGetDoubleField reads the string "1.5" as 15.

What it found nothing on

  • SemVer: 13 valid strings taken from the spec, 15 of the 19 invalid strings we tried, the printed precedence chain, and build metadata were all correct. All 21 breaks of GetField and all 6 of CompareNumericFields were caught.
  • JsonObject: ToSystemJsonObject (8 of 8 caught), ToJsonNode (10 of 10), Read (5 of 5), ContainsField (3 of 3). A 562 KB file with long escaped strings read correctly, and from that we judged the pooled buffer in Read latent. That was wrong, and the control run below proved it: "all breaks of Read caught" did not mean Read was right.
  • osu!: all 41 breaks of the nine HitResult questions the tests ask about (IsHit, IsBonus, AffectsCombo and the like) were caught, and so were all 8 of ApplyBeatmap, all 11 of updateScoreMultiplier and all 5 of GetComboScoreChange. By hand, a reverted hit put the score, combo and accuracy back, and each rank's cutoff gave that rank.

Who found what

Be accurate about this. The defects above were found by an agent reading the code against each rule while writing the model: the requirements step. The breaks did not find them. The breaks measured how much the tests hold, and showed where no test looks: 9 breaks of JsonObject.Equals got past every test, and that is where the crash was. No graph neural network (GNN) played a part in any finding here.

The control run: the loop against careful reading

The trials above could not say whether the loop beats reading the code carefully, so we ran that comparison on the two Unreal classes.

Each class got two agents on the same model with the same brief, in sandboxes of their own holding a copy of the class, its tests and its contract: one with the closed loop and told to use it, one without. A scan of their transcripts found neither had read our findings above. Every claimed defect had to come with a C# program, and our harness compiled and ran each one, so nothing rests on an agent's word: none failed to compile and none hung. Three graders per class then read both reports with the arms' names hidden, beside what the harness printed.

SemVer - Without the loop: 21.9 minutes, 294,903 tokens. With it: 36.3 minutes, 414,499 tokens. - Real faults: the graders counted 4 or 5 distinct ones depending on how they grouped them, the same ones in both arms. No grader found a real fault in only one arm. - Questions for the owner: 6 without, 7 with. Wrong claims: none. - Better report: tie, tie, and one slightly for the loop, which traced each fault to its cause and line more closely.

JsonObject - Without the loop: 31.4 minutes, 389,792 tokens. With it: 33.0 minutes, 480,628 tokens. - Real faults: 11, 12 or 14 distinct ones depending on the grader, the same ones in both arms. No grader found a real fault in only one arm. - Questions for the owner: 17 to 19 without, 23 to 25 with. Wrong claims: none. - Better report: tie, tie, and one for the arm without the loop. All three graders found that the arm with the loop called more undecided things defects: 6 to 8 of them against 2 to 4.

What this says. On finding defects in a class that has a written contract, the loop added no defect, and it cost more: 1.4 times the tokens and 1.7 times the minutes on SemVer, 1.2 times the tokens on JsonObject. An agent reading carefully, with no tool of ours, found everything the loop arm found. It also found far more than our own first pass above, which spent most of its budget on the tool's bugs.

What it does not say. This is one run per class, on one model, so it is a sign and not a measure. It tested finding defects. It did not test how much the tests hold, which is what breaks are for: neither agent was asked for that number, and a reader cannot get it by reading. The loop arm's extra questions rest partly on breaks no test caught, and the graders split on what those are worth.

Faults the control run found that we had missed, each proven by the harness on the code as shipped: - Read and TryRead parse a file over 128 KiB from a pooled buffer they have already returned. A valid 173 KB file with a very long name came back with other fields silently replaced, while Parse of the same text read it correctly, and a second file made Read throw FormatException. - Name matching uses a culture comparer, so names that are different strings can count as one field. - RemoveField and AddOrSetFieldValue ignore the empty name, which RFC 8259 allows. - NaN and infinity can be set, and then ToJsonString cannot write them. An object parsed 64 levels deep cannot be written either: it reports a cycle that is not there. - TryGetEnumField throws on a struct that is not an enum. - CreateDeepCopy shares reference values it does not know how to copy, and throws on keys that differ by case and on a multi-dimensional array.

What went badly

The trial's biggest finding was in our own tool. Real code broke it five ways on the first attempts, and a sixth way on osu!, none of which our own examples had shown:

  • It silently skipped code. Any method with overloads, any operator, any generic method with a where clause and any property body was left out, and the report still read as if the whole file was held. On SemVer it saw 35 of 68 statements, missing the private Compare that does all the comparing. On JsonObject it saw 213 of 288.
  • It crashed on read-only files, which is how a Perforce workspace keeps them, on the first run.
  • It mistook a nested type's constructor for a method, and stopped.
  • One mutant with broken braces stopped the whole run.
  • An endless loop in a mutant tested alone hung the run: 11 minutes on one test host before we killed it.

It also could not read MSTest or xUnit tests' /// CHECKS: lines, only NUnit's, and it took a parameterized test's arguments for part of its name, so it reported named tests as never run. Because that fix came after osu!'s pass, its per-requirement check results are not quoted here. All of these are fixed, each with a planted test. A field's value and an indexer are still not walked, and the report now names them.

Our earlier figures on one shop feature came through nearly unchanged, because that code has no overloads: 96.5% of 1,097 breaks became 96.4% of 1,104, and 290 of 313 statements became 293 of 317. No existing verdict changed. The 7 new breaks found one real gap.

The budget did not hold. We set 45 minutes and 150K tokens per trial and spent about 100 minutes and over 260K output tokens, most of it on the tool's own bugs. A full pass took 13 minutes on SemVer, 9 on JsonObject and 74 on osu! (each constructor break rebuilds the game), at low priority on a busy machine. The earlier-budgeted 60 minutes for osu! did not hold either.

Re-running it

The models are in t7/ beside this file. For the Unreal trials, copy EpicGames.Core, EpicGames.Core.Tests and their props files from your own engine to a scratch folder and run closed_loop.py on the model; numbers may differ on another engine version, and these are from 5.7. For osu!, clone ppy/osu at commit 845336e, keep the three test files under osu.Game.Tests/Rulesets/Scoring, and run it the same way.
