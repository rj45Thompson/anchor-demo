How the GNN works, what it records, and how it tries to improve

How it works

  1. It reads. Each node starts as its own words, hashed to 512 numbers.
  2. It listens. GraphSAGE layers let each node hear its neighbours, relation by relation. After that a node's numbers say something about what surrounds it.
  3. It ranks. A scorer ranks every requirement for a decision that has no owner.
  4. It asks. Below 70% sure it abstains. Above that, its answer goes out as a question for a person or an exact check. It is never a verdict.

It never reads breaks, tests or chains. Those hold the answer, and new code would not have them. Two ways that answer leaked in were measured and closed before any score here was taken. Whole methods are held out when it is tested, so each score is on code it has not seen.

What it records

  • Its score beside the plain rules, on each pass run with --gnn (stats.jsonl): GNN 0.76 over four seeds (0.74 to 0.79), the best plain rule 0.67, words 0.50, random 0.19, the same method 0.13, in mean reciprocal rank, where 1.0 is always ranked first. 3 of the shop feature's 7 passes ran it.
  • Each job against the best plain rule (kg/gnn_tasks.jsonl): who owns new code, which tests catch a break, which steps carry a requirement, which breaks are the same program. The results.
  • The shape of what it reads: 562 nodes, 1,570 links, 553 of them owner links, 41 methods, and how those links pile up: 3 requirements hold 56% of them, and 8 hold 80%.
  • Breaks ranked (kg/survivor_rank.jsonl): a learned order finds 50% of the survivors in the first fifth of a run, on average over ten seeds, against 31% for the plain rule and 21% for random. One seed flatters: this one ranged from 35% to 64%.
  • Its curve (gnn_curve): 0.48 with a tenth of the links, 0.77 with all of them.
  • How sure it was: at 70% sure or more it was right 92% of the time, on about 40% of new code (25% to 58%), over four seeds.
  • Every tune (gnn_tune.jsonl): each variant's score, and what was kept.

How it tries to improve

Its lead over the plain rules is itself a stat. On the shop feature that lead fell from 0.23 to 0.15 to 0.12 as more tests arrived, and the telemetry reports it as worsening and names reshaping the graph as a next job, beside writing tests. A tune is due after 5 passes without one anyway. A standing tick or a person then runs it: graph_gnn.py tune <graph>. A tune redraws what the GNN reads, with each relation left out and each derived link added. A change is kept only if it wins by 0.02 on the tuning seeds and again on a seed it was not chosen on.

So far

Measured 2 tunes, 14 variants, nothing kept. The best reached 0.750 against the full graph's 0.737, which is short of the bar. It attempts to improve itself, and the attempt has not paid yet.

Open A project's run plan records whether each learned job wins there, and so far only 1 of its 7 switches reaches what a pass runs.

The GNN: who owns new code?

When someone adds code, the loop needs to know which requirement it belongs to. The GNN (a graph neural network, a learning model that reads the graph) suggests an answer. It looks at what is already linked around that code and ranks the requirements from most to least likely owner.

How it was tested fairly

It was trained on part of the shop feature’s graph, with whole methods hidden from it. Then it was asked to rank owners for the hidden methods, code it had never seen. It was compared against simple rankers that do not learn, such as “the requirements already linked to this method” or “the requirement whose words overlap the code’s names most”. It is only allowed to make suggestions if it beats them.

What the numbers mean

MRR (mean reciprocal rank) scores a ranking: the right owner ranked first scores 1, second scores ½, third ⅓, and so on, averaged over every test case. An MRR of 0.75 means the right owner is usually first, sometimes second.

Where these numbers come from

Measured On the shop feature, with whole methods held out, measured three ways: a separate check on the pass 5 graph gave MRR 0.75 against 0.66 for the best ranker that does not learn, with the right owner in its top three 90% of the time; the loop’s own check inside pass 6 gave 0.79 against 0.67; and the fullness curve on the pass 5 graph, two seeds, every claim seen, gave 0.77 against 0.67. The check inside pass 5 itself read 0.63, before the strongest plain ranker was part of that check. Runs differ by about a tenth, so a single number is never the whole story.

Measured It only wins on a large enough graph that is about half claimed: see Seed it first, then it flies.

Measured When the GNN said it was at least 70% sure, it was right 92% of the time, over four seeds. It was that sure for about 40% of the new code, from 25% to 58% by seed. For the rest it says “not sure” and asks. (Measured again on 30 October on the grown graph; on an earlier graph it was 94% on about half.)

Its suggestions are always questions for a person, never verdicts. One lesson from building it: the first version did worse than the simple rankers, because the links it was asked to predict were also links it could read. Separating the two fixed it.

Shaping the graph for the GNN

The GNN learns from the graph’s links, and not every kind of link helps it. A tuning pass tries leaving out one kind of link at a time (for example the link from every branch to the one shared “space” node, which ties everything to everything) and measures the GNN again on code it never saw. A change is kept only if it helps on the tuning runs and again on a separate run it was not chosen on, so that a lucky result is not mistaken for a real one. The kept choice is written beside the graph, and the GNN reads it from then on.

The stats decide when to tune: when the GNN’s lead over the simple rankers stops growing, or every five passes otherwise (how the stats choose).

The first tune, on the shop graph

Measured The full graph: MRR 0.737 (0.747 and 0.726 on two runs, so the run-to-run noise alone is about 0.02). Six variants were tried. None beat the full graph by the required 0.02, so nothing was changed. The best, leaving out the use-case structure links, gained 0.012; leaving out the shared “space” node gained 0.009.

Measured The links the GNN relies on most: “binds requirement” (leaving it out costs 0.016) and “is at”, which ties a branch to its method (costs 0.012).

The second tune: adding links, three runs each

Measured Adding links the graph lacks did not help beyond the noise: linking the methods of one class +0.005, linking requirements one step carries together +0.003. Leaving out the use-case structure links was the only change never worse on any run (+0.013 on average), still under the 0.02 bar. Nothing was changed.

What that says: on this graph the GNN already gets what the structure can give it. The next gains are more likely from more graphs to learn from and better descriptions of each node than from reshaping this one.
