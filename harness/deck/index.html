What a planted bug is, and when it changes nothing

10

Slide 10: what the speaker says

This is mutation testing: each planted bug is one small change to the code, and a test should fail because of it. Up to 24 planted bugs a statement, one of each kind first. One limit on every: until this week the C# adapter skipped overloads, operators and property bodies without saying so, and it still does not walk a field's value or an indexer, which the report now names; slide 15 has the numbers. A planted bug that every test passes is either a missing test or the same program. Same program is proven by comparing compiled code, Trivial Compiler Equivalence from Papadakis and others, 2015. Anything else needs a reason in writing, and a declared equivalent that a test ever kills is a hole, not a pass. Self-improvement is on by default because the tool tests itself. Every pass writes one row of stats, checks them against requirements on those stats, and prints what to improve next. That is cheap. Experimental · The loop, in pseudo C++

One pass, then one tick

// One pass. Self-improvement is on by default.
Verdict run(Model& m, bool selfImprove = true) {
  Breaks  b = Mutate(m.code);       // one compile
  Results r = RunEachAlone(b, m.tests);
  Graph   g = KnowledgeGraph(m, r);
  Holes   h = Criteria(g);          // 18 checks

  if (self_improve_on(m, selfImprove)) {
    Row row = PassStats(m).collect();  // 44 stats
    MorphLog(m).add(row);
    auto fired = improvement::fires(rules, log);
    Print(NextImprovement(log, fired).picks());
  }

  return h.ours.empty() ? HOLDS : OPEN;
}

// One tick. A fresh agent, one item, no memory.
void Tick() {
  Start s = loop_tick::start();     // the lock
  if (s.stopped || s.busy || s.idle) return;
  if (s.epochStarts) Brainstorm();  // every 12
  RunSelftests();                   // red = item
  telemetry_audit();                // unread = item
  Item i = Choose(improvement::check(), board);
  Stat before = i.stat.Measure();
  i.Do();                           // one change
  Stat after = i.stat.Measure();
  if (s.epochEnds) {
    run_plan::decide();            // parts on or off
    improvement::graph();           // did it work?
  }
  loop_tick::finish(i, before, after, worth);
}

The same shape, one level up: stats are its code, triggers its requirements, ticks its tests. Three ticks worth “no” in a row and it sleeps until something changes.

The graph network’s whole story, and its numbers

24

Slide 24: what the speaker says

Every learned part of the tool was held to one rule: it must beat a plain rule that does not learn, on code it has not seen, or it is switched off. The graph neural network lost. On the tool's own code it ranked the right owner of new code at 0.65 against the plain rule's 0.72, so it was retired on 3 November. One rule stays in the switch file: when a project's graph reaches 5,000 entities it is tried again, and it must win by more than 0.02. Its other jobs need no guessing any more: which test catches which planted bug is read off the test runs themselves, and a bug that changes nothing is proven by comparing compiled code. Two other learned parts are off as well: the pick of a step's requirements lost to plain similarity, and neither is used now, because the author binds each step's requirements and the model rules refuse a step that binds none, and the learned order for running the planted bugs, which did beat its plain rule, was retired because the break-order head shown next does that job. Switching off what does not beat a simple rule is the point: the record says why each part is off and what would wake it.
