Self-improvement, on by default

The tool tests itself, and that is on unless you turn it off. It happens at two sizes.

Every pass. A pass writes one row of stats about itself to the morph log, checks those stats against the tool's own requirements for improving, and prints what to improve next. Nothing about your code changes.

The standing tick. A fresh agent with no memory takes one item, measures the same stat before and after the change, and records whether it was worth it. Both ship in this kit, with the self-improving qualities we built for our ARC3 harness. Nothing starts a tick for you: TICK.md is its runbook, and you schedule it.

Turning it off

Run with --no-self-improve, or put self_improve: false in the model's loop: block. The pass then records no row and prints no picks. There may be some token saving, but on a pass it is small; the larger spend is the tick, which only runs if you schedule it, and stops when you stop scheduling it or create .loop_tick.STOP beside the tools.

Where these numbers come from

Measured A pass: 44 stats in a row, about a third of a second to collect them, three printed lines for the agent to read. On the kit's Python example, a clean install, with it off a pass wrote no row and printed 295 fewer characters.

Measured A tick: the app counted 197,134 tokens for the first tick and 291,042 for the second, over 9 and 22 minutes.

One shared graph, not networked in this version

Ideally everyone working on a project shares one graph, because it also works as a retrieval store (retrieval-augmented generation, RAG): an agent looks up what is already proven instead of re-reading the files to work it out again. We share ours across the team that way to save tokens. This version is not networked, and each checkout keeps its own graph; you could add sharing in whatever way suits your network.

The loop, in pseudo C++

The toolkit is written in Python. This is the same logic for a C++ reader; the lower-case names are the real ones in the code.

// One pass. Self-improvement is on by default.
Verdict run(Model& m, bool selfImprove = true) {
  Breaks  b = Mutate(m.code);       // one compile
  Results r = RunEachAlone(b, m.tests);
  Graph   g = KnowledgeGraph(m, r);
  Holes   h = Criteria(g);          // 18 checks

  if (self_improve_on(m, selfImprove)) {
    Row row = PassStats(m).collect();  // 44 stats
    MorphLog(m).add(row);
    auto fired = improvement::fires(rules, log);
    Print(NextImprovement(log, fired).picks());
  }

  return h.ours.empty() ? HOLDS : OPEN;
}

// One tick. A fresh agent, one item, no memory.
void Tick() {
  Start s = loop_tick::start();     // the lock
  if (s.stopped || s.busy || s.idle) return;
  if (s.epochStarts) Brainstorm();  // every 12
  RunSelftests();                   // red = item
  telemetry_audit();                // unread = item
  Item i = Choose(improvement::check(), board);
  Stat before = i.stat.Measure();
  i.Do();                           // one change
  Stat after = i.stat.Measure();
  if (s.epochEnds) {
    run_plan::decide();             // parts on or off
    improvement::graph();           // did it work?
  }
  loop_tick::finish(i, before, after, worth);
}

Three ticks in a row worth "no" and the tick sleeps until something it watches changes, so an idle loop costs almost nothing. The improvement graph is the same shape one level up: stats are its code, triggers its requirements, ticks its tests.

The loop on its own improvement

The loop records a great deal about itself: every pass leaves fifty numbers, and the learned parts leave evidence of when they help. Recording a number is only worth it if something reads it and acts. On 29 October an audit found 28 numbers that nothing read, and many more that were only printed.

So the improvement of the loop now has requirements of its own, written the way the product's are. Each number has a requirement saying what pattern in it should trigger something, what that is, and why the number is kept: a test that catches nothing for two passes is a speed item; an excuse for a harmless break that lapses is a hole; the graph not growing for three passes means the model is not being seeded. A number kept for a learner that does not exist yet must name that learner and a date. Past the date, unread, it fails.

Three levels, one graph

  • Level 1, the product. The loop holds the code to the product's requirements.
  • Level 2, the improvement. The loop holds itself to its improvement requirements, with the same kind of closure rules: every number covered, every trigger that fires acted on, every action naming the number it meant to move and its result measured, and an action that never moves its number retired.
  • Level 3 is level 2 again. How well the improvement graph is doing (numbers covered, triggers acted on, actions that worked) is itself written as numbers with requirements, so they sit in the same graph. The tower closes on itself.

The same learning applies one level up: once enough actions have measured results, a model can learn which kind of action moves which number, and it is switched on only where it beats the plain rule, like everything else.
