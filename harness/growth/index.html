Kill rate, project by project

What it is. Of the breaks the loop made in the code that a test could judge, the share a test caught. Breaks shown or declared to change nothing are left out, and so are breaks with no verdict.

What a rise does and does not prove. A rise proves a larger share of the judged breaks was caught, or that more survivors were explained. It does not prove the tests got better.

In the kit’s Python example the kill rate rose from 0.9565 to 1.0000 while the count of breaks caught stayed at 66 on every reading, so the rise came from breaks being explained, not from more being caught.

The rate leaves out breaks with no verdict. The largest share is in one game feature: 52 of 1,104 breaks had none.

The axis starts at 0.50 where no reading is lower.

The tool’s own code: its two readings are not comparable (the definition changed: the Python adapter now decides by bytecode which breaks change nothing, so breaks once set aside as equivalent are judged).

What a rise does and does not prove. A fall means holes were closed. A rise does not mean the code got worse: the tool is changed between readings, and when it learns to look for another kind of gap the count rises on code that did not change.

The largest rise in the kit’s Python example went from 0 to 12 between 10-29 18:25:51 and 10-29 21:37:22, while the tool changed from 5,835 to 5,994 lines. The code under test was not what changed first; the tool was.

The owner network’s score, project by project

What it is. How well the network that guesses which requirement owns a piece of code ranks the right one, as a score from 0 to 1 (mean reciprocal rank: 1 means the right requirement is always first). Only a pass that ran the learned part writes it.

What a rise does and does not prove. A rise means the network ranked the right requirement higher on that pass’s graph. The graph and the model change between passes, so two readings answer slightly different questions: it does not prove the network got better.
