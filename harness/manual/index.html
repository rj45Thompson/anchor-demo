The key is accuracy

Accuracy boosts productivity across the board. In our view it makes AI, in some cases, thousands of times smarter. That multiplier is our view, not a measurement: the largest multiplier we have measured is 216 times less reading.

The gap between what AI guesses and what is true is what people deem AI slop. At TNT Tools the standard is no slop: every value is either read from a source, with a note of where, or marked absent with the reason. There is no third kind.

Where these numbers come from: our knowledge graph, on facts

Measured 99.03% of 35,951 derivations it had never seen were right, using reasoning rules guarded by type, on a verified-or-abstain knowledge graph of 60.33 million facts, each carrying which sources state it.

Measured 616 of 616 of its top-tier facts were right against an outside truth (cached Wikidata), on a frozen test population of 2,714 entities, with the bars declared before the run.

Measured 99.2% right on 209 held-out questions, answering 61% of them and abstaining on the rest. Asked the same questions on the same facts, a local language model answered 95% at 98.0%, with 4 confident wrong answers. The accuracy comes from being allowed to say "I don't know".

Those are facts, not code. On code, the numbers are in one feature over five passes and six kinds of task, and the target for agents writing code with the loop is still a target. Graders on those tasks counted 17 invented values with the loop and 5 without, so "no guesses" is the standard being worked toward there, and the count is how we know.

Back to 1999: requirements first

This is how we review our code: we pour the effort into requirements first. It is time to learn systems analysis and design again. Agile is, for the most part, dead. Long live waterfall.

The reason is mechanical. The more requirements you have, the better a graph neural network (GNN) works at filling the gaps, and the more of the loop closes, so that nothing is left to a guess. That is what gets you slopless code. We want hand-crafted quality on an IKEA budget.

Where this comes from

Measured On the shop feature, the graph neural network (GNN) scored 0.48 with a tenth of the requirement links, 0.63 with a quarter, 0.73 with half and 0.77 with three quarters or all, against 0.67 for a plain rule with no test results to read. See seed it first. Once test results exist, a plain rule that reads them does better on that feature: see the part that learns.

There is no such thing as "we don't use AI"

AI is a first-class testing tool first, and a code writer second. Write every line by hand if you like: it will still tell you which of your tests cannot fail, and which code no test notices. When it does write code, it is held to the same requirements and the same tests as everyone else.

There is no reason to throw away really well done tests. That is the baby with the bathwater. Your tests become the judge of what AI does.

Where it comes from: a mutation of an ARC3 self-improvement loop

This toolkit is not only a shop feature's numbers. It is a mutation of the self-improvement loop from our ARC3 harness, which was a piece of a failed attempt at AGI. The shop feature, a weapon shop among the examples, is what we built this version on, because our own is internal and cannot be extracted. What came across is the part that survived: propose, then verify; abstain rather than guess; and never trust a number you could game.

The point of all of it

Testing raw: AI that tests the requirements

We test code. Requirements get reviewed by people, now and then. What AI adds is requirements testing done by a machine, all the time, at the scale of the code. This loop is built for exactly that.

The requirements are the code behind the code. When an agent writes the program, it writes it from the requirements, so in its rawest form the requirements are the code. A mistake in a requirement becomes a mistake in every line written from it. Testing before that stage, on the requirements themselves, is what we call testing raw.

It makes new requirements by finding failures in the ones it has. The loop walks each use case step by step and asks what every step needs. When a step needs something no requirement provides, that gap is a failure of the requirements, and it becomes a new requirement: marked inferred, and put to the owner as a question.

Measured

Measured On the shop feature, walking the use cases found 10 requirements nobody had written, beside the 17 the designers wrote. Each went to the owner as a question, for example “what raises a shop’s level?”.

Measured On an earlier tool for the same game, the same method inferred 7 requirements; all 7 were real defects, and none of them was in the written requirements.

The code still gets tested. Breaking the code on purpose (how) is how the loop checks that each requirement really reached the code. But the requirements are tested first, because that is where a mistake is cheapest to catch.

Very little work has been done on AI requirements testing yet. As agents write more of the code, the part people write is the specification, and the work moves back toward writing it first, closer to waterfall. Testing that specification becomes the main job, and that is where this loop puts its effort.

The idea in one minute

When an AI agent writes code, it usually finishes by saying it is done. Most of the time you cannot check that without reading everything it did. The closed loop makes “done” something a machine can check.

Think of a building inspector with the plans in hand. The plans are your requirements, written down as data instead of as a paragraph. The inspector never takes the builder’s word. It checks every item on the plans against the building, and for every part of the building it asks which item on the plans that part is for.

What keeps the inspection honest is that the inspector also breaks things on purpose. It takes a piece of working code, changes it slightly so it is wrong, and checks that at least one test notices. If no test notices, nothing is really checking that code, whatever the test report says.

At the end you get a count of three things: breaks no test noticed, code no requirement asked for, and questions only the owner can answer. “Done” means that count is zero.

Why a count and not a feeling

“Did I think of every requirement?” has no answer: what you forgot leaves no trace. “Is the list of open questions empty?” does have one, because the list is generated from the plans and the code, not from memory. So the loop never tries to be complete by writing more. It walks the plans, and every gap it meets becomes a question with a file and a line.

It extracts new requirements from the ones you have

The tool automatically extracts requirements from existing requirements. You do not list them by hand. It walks each use case step by step: every step needs something to be true, and when no requirement provides that, the chain has inferred one nobody wrote. It is marked inferred and goes to the owner as a question, because only the owner can decide it. See the idea in one minute for what that found on the shop feature, and growing a model from a small seed for how far it went from 3 requirements.

Complete in, accurate out

The more complete the requirements, the more accurate the prompt built from them: an agent acting on them has less to guess. Which ones you write first matters as well, so start with the ones that run through the most code (seed it first).

Remix, don't invent

When adding a large feature, it is probably better to remix two features that already have solid requirements than to invent something new with no clear ones. Adding a weapon shop, say, is a remix of a shop and an inventory, and a shop is one of the examples this tool was built on. A remix starts from requirements that have already been tested, so the gaps it leaves are the places where the two meet, and the walk finds those. A new invention starts with nothing to walk.

Open This is our judgment from building with it. No run has measured complete against incomplete requirements, or remix against invention, directly.

Why use it

Requirements written as prose cannot fail

A paragraph saying “the player can buy an item if they have enough money” never turns red when the code drifts away from it. The loop keeps each requirement as a record with an id, its source, and the code it points at, so a requirement that no longer matches the code shows up as a failure.

Tests can pass for the wrong reason

A test that checks the price shown on screen passes even if buying never takes the money out of the wallet. Every test is green and the rule is broken. Breaking the code on purpose finds this: take the line that subtracts the money out, and see whether any test fails. If none does, the rule has no test, however many tests there are.

Long runs forget

An agent’s working memory (its context window) fills up during a long job, and early details drop out. Later steps then guess at what was settled before. The loop writes everything it learns to a graph on disk, so a later step looks the answer up instead of guessing it again. Every entry says where it came from.

On the slides: slide 4.

When it fits, and when it does not

Use it for larger systems: code that many changes will touch, where a rule must still be true after the agent’s tenth edit as well as its first, and where you want to know which line exists because of which requirement. It also helps most when agents run for hours, across many context windows.

Skip it for a one-off prompt, a quick script, or exploring an idea. The loop costs setup and run time, and it pays that back only when the same requirements are held across many changes. It is also no help with how something looks or feels: visuals, timing and feel still need a person.

Why a thin model can be worse than nothing

The loop can only check what is written in the model. Suppose the model holds three requirements and two tests. The loop may honestly report everything closed, because everything it knows about is checked. But a green report reads as “the work is complete”, when all it proves is that three small things are right. That false confidence is worse than having no report at all.

How large a model must be before its report means something is only partly known. The first measurements are in Seed it first, then it flies. Until there are more, treat a green loop over a small model as “these few things hold”, never as “it is done”.

Open How many requirements, tests and graph nodes are “enough” for the whole report is not known yet; for the part that learns there is a first answer.

Seed it first, then it flies

The loop learns from what is already written down. Give it a model with a handful of requirements and it can check those few, but it has little to reason from when new code arrives. Give it many, with their code claimed, and it starts to see the patterns: which requirement a new branch most likely belongs to, which questions follow from which. So the order of work is: seed the model with as many sourced requirements as you can, then let the loop carry it.

How full is full enough

We measured this for the part that learns, the graph neural network (GNN). For each graph it was allowed to see only a share of the known links between code and the requirements that own it (a tenth, a quarter, half, three quarters, all of them), always tested on methods it had never seen, and compared with a plain rule that does not learn: “suggest the requirements whose effects already sit in this method”.

Some requirements are pillars

Which requirements are written matters as much as how many. A few carry most of the code. On the tool’s own model, 7 of the 12 requirements that own any code own 80% of it, and one of them runs through 16 methods. Seed those first: a rule that runs through many methods gives the rest of the graph something to attach to.

The smallest seed that grows into the whole loop

The loop already grows requirements. It walks each step, asks what the step needs, and every need nobody wrote becomes a new requirement for the owner to settle. On the shop feature, 10 of the 27 requirements were inferred that way, on top of the 17 that cite a written source. So the open question is how small the written set can be and still grow into the full model. A small, well-chosen seed would mean less to write up front, and a structure that is easier to keep consistent.

How to run it

  1. Install. python install.py puts the skill where Claude Code finds it and the tools beside it, then runs every selftest and the whole loop on a small example project. The example must pass (“hold”), or the install says so. See Install.
  2. Write the model of your system. First the problem story in your own words, each sentence with its source. Then the requirements, each pointing at the code it is about. Then the use cases: who wants what, step by step. Then a short block that names your code folders and your test files. python -X utf8 usecase_model.py <model> checks the 19 rules (see The model).
  3. Run the one command. 
    CLOSED_LOOP_ROOT=<your repo> python -X utf8 closed_loop.py run <model> --out REPORT.md --pin-claims "<why>"
    It breaks your code every way it knows, runs your tests against every break, builds the graph, applies the 17 checks and writes a report.
  4. Close what is yours. The report sorts what is open into two kinds. Yours: a missing test, a line no requirement claims, a break that changes nothing and needs explaining. The owner’s: questions about what the system should do, which only the person who owns the requirements can answer.
  5. Take the lock. When nothing of yours is left, --accept "<why>" records the verified state. A later change to that code makes the affected requirements stale until they are verified again. The lock refuses while any hole of yours stands, so it can never be used to turn a red report green.

Part 2 · The pieces

One pass, end to end

  1. The model is read and checked against its 19 rules.
  2. The code is broken: every statement the requirements cover, every way the tool knows, all built at once.
  3. The tests run against each break separately. Each break should make some test fail.
  4. Everything goes into the graph: requirements, steps, code places, breaks, tests, and which test caught which break.
  5. The 17 checks read the graph. Each one is named after a mistake it stops.
  6. The verdict is either HOLDS, or OPEN with a list of questions and whose each one is.

You close your questions and run again. That repeat is the loop.

On the slides: slide 8.

The model: your requirements as data

The model is a few small text files (YAML) beside your code:

  • The problem story: one paragraph on what the system is for, each sentence with where it came from (a person, a design document, a date).
  • Requirements, each with an id, its text, how to check it, its source, and the code it points at. A requirement is authored (someone wrote it) or inferred (the loop found that a step needs it and nobody wrote it). Inferred ones are questions for the owner, never facts.
  • Use cases: who wants what, as 3 to 11 numbered steps, plus what happens when a step cannot complete. Each step names the requirement it relies on.
  • The loop block: which code folders and test files the loop works on.

The 19 rules refuse a model that is malformed before anything runs. Some examples of what they refuse, in their own words: a use case with too few or too many steps; “step 3 carries no requirement”; “a requirement with no text”; “no measure: nothing says how to check it”; a story sentence with no source; two items sharing one id; a use case with “no alternate pathway: what happens when a step cannot complete?”; a requirement carried only by summary steps, so no real user goal ever reaches it.

Breaking the code on purpose

The usual name is mutation testing, and each broken copy is a mutant. This manual calls them breaks. A break that makes some test fail is caught (or “killed”). A break that every test still passes got past (or “survived”), and that points at a missing test.

A small example

if (wallet.Money >= price)   // the real code: exact money is enough
if (wallet.Money >  price)   // a break: paying the exact price now fails

If every test still passes with the second line, then no test buys something with exactly enough money. That is a missing test, and the report names the line.

The kinds of break the C# adapter makes, in plain words:

  • Conditions: turned around, forced always true, forced always false.
  • Operators: < made <=, == made !=, && made ||, plus made minus.
  • Values: a number made one more, true made false, a text emptied, a function argument replaced by its default.
  • Structure: the two outcomes of a ? : swapped, an else branch removed, a statement removed, the whole method made to return at once.

Each statement gets at most 24 breaks, one of each kind first, so a busy statement cannot crowd out the kinds of break that matter most.

Why it is fast enough

Building each broken copy separately would mean hundreds of compiles. Instead, every method is copied once per break inside one build, and a switch picks which copy runs. One compile serves every break. A copy that does not compile is found by the line and column of its error and dropped, and the rest are rebuilt.

Each break then runs the tests alone, in its own copy of the build in a temporary folder. The live project is never touched.

Where these numbers come from

Measured On 29 October, pass 4 on the shop feature (see the test subject) made 772 breaks. Compiling all of them once took about 45 seconds. Each break then ran the shop’s tests in about 3 seconds, two at a time, so the whole pass took about 20 minutes on one desktop machine.

The right test must notice

It is not enough that some test fails when a requirement’s code is broken. It should be that requirement’s own test. Otherwise the requirement is only protected by accident: a test written for something else happens to fail today and may not tomorrow.

So each test says what it checks, on the line above it:

/// CHECKS: W-1
[Test]
public void Pay_TakesExactlyThePrice() { ... }

A requirement whose named test misses its own breaks is a hole, even when another test caught them. And a test named as a requirement’s check that catches none of that requirement’s breaks is a hole too, so listing more tests can never make the score look better.

On the slides: slide 3, slide 21.

Breaks that change nothing

Some breaks get past every test because they do not change what the program does. Example from the shop feature: the cursor moves by the sign of a number, so changing a 1 to a 2 there moves it the same way. No test can catch that, and none should. These are called equivalent breaks.

The danger is calling a real missing test “equivalent” to make it go away. So the loop accepts an equivalent in only two ways:

  • Proven by the compiled code. C# compiles to IL, the instructions the runtime actually runs. If the broken copy’s IL is identical to the original’s, the two are the same program (a technique called Trivial Compiler Equivalence, Papadakis and others, 2015). The loop checks this itself.
  • Declared with a reason. Otherwise a person or agent writes down why it changes nothing, and names the methods the reason depends on. If those methods change later, the reason lapses and the break is counted as a hole again.

And if a test ever does catch a break that was declared equivalent, the declaration was wrong, and that is reported as a hole. This happened twice on the shop feature: two breaks looked harmless (one about how a German computer writes the number “2.0”, one about an invisible zero-width character before a “#”), but each could change the result. Both are now held by tests instead.

On the slides: slide 9.

Claims and locks

A claim says “this method belongs to requirement X”. The loop pins each claim to a fingerprint of the method’s statements. If someone adds a line to that method or deletes one, the fingerprint changes and the claim goes stale. A new line can never slip in under an old claim without being looked at.

The pins are kept in a small file (claims.lock). If that file goes missing, every claim is unpinned until a person pins them again with a reason. A missing lock never quietly re-pins itself; a reviewer found that it used to, and it was fixed.

The node graph, and flying through it

Everything the loop knows about a feature is one graph: who asked for what, which code does it, every way that code was broken, and which test noticed. The shop feature's graph has 1,714 nodes and 10,024 edges. It is stored as SQLite and N-Triples. The fly-through demo draws that store as it is, with nothing added and nothing left out. The pictures behind the slides are stills from the same page.

How it is laid out

The store has no shape of its own, so the demo gives it one you can read from top to bottom, one ring for each kind of node:

  • Why it exists: 19 sources, 27 requirements (17 written by people, 10 inferred by walking the use cases), 7 owner's questions, 6 use cases and their 32 steps.
  • Claude's reasoning: a chain and its 9 steps, each citing what it stands on.
  • What the code does: 50 methods in a ring, sorted by name, so a class's methods sit together.
  • What proves it: 313 branches, 1,097 breaks and 45 tests. Each branch and each break sits at the angle of the method it belongs to, so a method and everything under it line up.

How code maps to requirements

Two kinds of edge do it. A branch maps to a requirement: 620 of those. A branch is at a method: 313. Together they take you from any decision in the code to who asked for it, and from a requirement to all the code that answers to it. A decision no requirement owns is a hole, and the loop lists it.

The 130 breaks no test caught. The knowledge graph

A graph here is just a list of things (nodes) and the links between them (edges). The things are requirements, use case steps, places in the code, branches, breaks, tests and reasoning steps. The links say how they relate, for example:

requirement W-1   is checked by   test Pay_TakesExactlyThePrice
break #312        was caught by   test Pay_TakesExactlyThePrice
method Pay        is claimed by   requirement W-1

The graph is the record: the 17 checks read it, and a later agent reads it instead of re-deriving what an earlier one found. It is written on every run as a SQLite database and as an N-Triples text file, a standard format any graph tool can open.

The 17 checks

Each check is named after the mistake it stops. Each one is proven by a planted mistake: the tool’s own selftest builds a small model with that exact mistake in it and requires the check to catch it. A check that has only ever passed cannot be told apart from one that is switched off.

L1Identity. Things keep their identity across rebuilds, so a verdict never ends up attached to the wrong thing.
L2Sourced. Every requirement traces to something outside the model: a person’s words, a design document. Nothing is invented.
L3Corroborated. A requirement only one source states is listed, because it inherits that source’s mistakes.
L4Carried. Every requirement is reached by some path through the main use case. Otherwise nobody builds it.
L5Ended. Every path has an end and someone acting; every step carries something.
L6Answered. Every question was answered by a person, not settled by a guess.
L7Realized. Code linked to a requirement has the shape the requirement describes.
L8Falsifiable. A check must be able to fail. One that passes whatever the code does is a hole.
L9Justified. Code no requirement asked for is flagged: behaviour that slipped in.
L10Defined. A requirement names things the code really has, and uses each word one way.
L11Causal. Every step’s starting condition is made true by something earlier.
L12Consistent. No two requirements demand opposite things.
L13Change-safe. A requirement, or the code it reads, that changed after it was verified is stale until verified again.
L14Caught. Breaking a requirement’s code makes a test fail.
L15Pinned. Every branch is held by a test: break it any way and something fails.
L16Own check. The test that notices is the requirement’s own named test (why).
L19Equivalent. A break called “the same program” has a proof, or a reason no test refutes (why).

The numbering skips L17 and L18. L17 is a planned check from the research (vacuity: a requirement’s check must fail when its condition is forced off), not built yet.

Must and may: what “closed” means

The research behind the loop looked at how logicians describe “complete”. The closest fit is a Modal Transition System (Larsen and Thomsen, 1988). Every behaviour is marked either must (it has to happen) or may (it is allowed, not yet decided). A specification is finished when no “may” is left: every open choice has been settled one way or the other.

Here, the authored requirements are the musts. The inferred ones, the things the steps need that nobody wrote, are the mays. Each may is a question for the owner, who settles it as a must or as “either is fine”. On the shop feature, “what raises a shop’s level?” is one such may: the code needs it and no one has said.

How the GNN works, what it records, and how it tries to improve

How it works

  1. It reads. Each node starts as its own words, hashed to 512 numbers.
  2. It listens. GraphSAGE layers let each node hear its neighbours, relation by relation. After that a node's numbers say something about what surrounds it.
  3. It ranks. A scorer ranks every requirement for a decision that has no owner.
  4. It asks. Below 70% sure it abstains. Above that, its answer goes out as a question for a person or an exact check. It is never a verdict.

It never reads breaks, tests or chains. Those hold the answer, and new code would not have them. Two ways that answer leaked in were measured and closed before any score here was taken. Whole methods are held out when it is tested, so each score is on code it has not seen.

What it records

  • Its score beside the plain rules, on each pass run with --gnn (stats.jsonl): GNN 0.76 over four seeds (0.74 to 0.79), the best plain rule 0.67, words 0.50, random 0.19, the same method 0.13, in mean reciprocal rank, where 1.0 is always ranked first. 3 of the shop feature's 7 passes ran it.
  • Each job against the best plain rule (kg/gnn_tasks.jsonl): who owns new code, which tests catch a break, which steps carry a requirement, which breaks are the same program. The results.
  • The shape of what it reads: 562 nodes, 1,570 links, 553 of them owner links, 41 methods, and how those links pile up: 3 requirements hold 56% of them, and 8 hold 80%.
  • Breaks ranked (kg/survivor_rank.jsonl): a learned order finds 50% of the survivors in the first fifth of a run, on average over ten seeds, against 31% for the plain rule and 21% for random. One seed flatters: this one ranged from 35% to 64%.

The GNN: who owns new code?

When someone adds code, the loop needs to know which requirement it belongs to. The GNN (a graph neural network, a learning model that reads the graph) suggests an answer. It looks at what is already linked around that code and ranks the requirements from most to least likely owner.

How it was tested fairly

It was trained on part of the shop feature’s graph, with whole methods hidden from it. Then it was asked to rank owners for the hidden methods, code it had never seen. It was compared against simple rankers that do not learn, such as “the requirements already linked to this method” or “the requirement whose words overlap the code’s names most”. It is only allowed to make suggestions if it beats them.

What the numbers mean

MRR (mean reciprocal rank) scores a ranking: the right owner ranked first scores 1, second scores ½, third ⅓, and so on, averaged over every test case. An MRR of 0.75 means the right owner is usually first, sometimes second.

Argument chains: holding the agent’s explanation to the requirements

Breaking the code checks the code. A chain checks the agent’s explanation of the code. When an agent finishes a change, it writes down, step by step, why the change does what the requirements ask: each step is one claim in plain words, plus what that claim stands on. The loop then checks every step against the requirements, the code and the graph.

A chain is a written argument the agent produces on purpose, like showing your work. It is not a recording of the model’s private thinking, and the tool does not try to extract that.

What a chain looks like

A real one, written by the agent that built the shop feature. It names the question it set out to answer, then its steps; each step says one thing and cites what it stands on: a requirement’s id, a question put to the owner, or a method in the code.

chain:
  id: CH-EXAMPLE
  question: "Does a purchase stop when the stock is gone?"
  steps:
    - says: "A limited line sells its quantity and is then sold out"
      cites: [W-3, Store.Buy]

The four checks

  1. Grounded. Every cite must exist: a requirement in the model, a question the owner was asked, or a method the code really has. A step that cites nothing, or cites something that is not there, fails the run.
  2. Same words. The step’s words should share at least one word with what it cites. If they share none, the step is flagged for a person (“a new finding, or a mistake”). This is a hint, not a failure.
  3. Joined in the graph. For every pair of things one step cites, the graph must already connect them within four links. The shortcuts that would make everything look connected are not counted: the chain’s own links, the shared “space” node, and the records of breaks and tests. A pair the graph does not join is either a link the model is missing or a mistake in the argument, and a person decides which.
  4. Blind spots. Every inferred requirement (an owner’s open question) that no step cites is listed: the chain never looked there.

The chain also becomes part of the graph: a node for the chain, a node for each step, and a link from each step to everything it cites. A later agent can see which explanations rest on which requirements.

How a chain meets the code

The chain does not sit beside the graph: it goes in. Take a step from the kit's example, “A limited line sells its quantity and is then sold out”, citing W-3 and Store.Buy. The step becomes a node with an edge to each of those, and both were already nodes. Then the graph walks from one to the other. Here a branch of that method maps to W-3, so the two are 2 links apart, and the report says so: “grounded; the graph joins every pair it cites”. The demo's tour follows a step like it on down through the code, a branch, a break of that branch and the test that caught it.

Buzzsaw testing: attacking the assumptions

Breaking the code attacks the code. Buzzsaw testing attacks what the requirements assume. Every model takes some things as given:

  • Inferred requirements: things a step needs that nobody wrote down. Only the owner can say if they are right.
  • Entry conditions: facts that come from outside the model, such as “a sheet line names an item the game has”.
  • Declared equivalents: breaks someone said change nothing, with a reason.

For each one, buzzsaw flips the answer (“what if this is not true?”) and walks the graph to find everything that rests on it: the later steps of every use case that relies on it, the requirements those steps carry, their effects, the code, and the tests that would have to change. That set is the assumption’s blast radius. The widest ones go to the owner first, because the most depends on them.

Measured on the shop feature

Measured 41 assumptions: 10 inferred requirements, 7 entry conditions, 24 declared equivalents. The owner’s widest question was “the player has a wallet the shops read and pay from”, with a radius of 79 (9 steps, 10 requirements, 12 effects, 11 code places and the tests on them). The game has no money system yet, so this is the question to settle first.

Measured 3 entry conditions that nothing reads any more. The code that read them moved when the screen was refactored, so they are stale and should be removed or re-pointed.

A lesson from building it

The first version said every assumption reached 33 steps and all 41 tests, so it could not rank anything. The summary use case (the epic) repeats requirements the detailed use cases carry, and walking on from the summary reaches everything. Starting the walk only from the most specific step that carries an assumption fixed it.

What it cannot do: it does not know which answer is right, and it measures how much depends on an assumption, not how likely it is to be wrong. Next: the same attack on the design spreadsheet’s values, by changing each value across its range and running the tests (Open).

Good requirements answer seven questions: who acts, what they want, why, when it starts, where it happens, what must be true before, and what is true after. The model has three levels where these can be asked: a use case, a step inside it, and an extension (what happens when a step cannot complete). Each level has a field for some of the questions and none for others.

Shaping the graph for the GNN

The GNN learns from the graph’s links, and not every kind of link helps it. A tuning pass tries leaving out one kind of link at a time (for example the link from every branch to the one shared “space” node, which ties everything to everything) and measures the GNN again on code it never saw. A change is kept only if it helps on the tuning runs and again on a separate run it was not chosen on, so that a lucky result is not mistaken for a real one. The kept choice is written beside the graph, and the GNN reads it from then on.

The stats decide when to tune: when the GNN’s lead over the simple rankers stops growing, or every five passes otherwise (how the stats choose).

Self-improvement, on by default

The tool tests itself, and that is on unless you turn it off. It happens at two sizes.

Every pass. A pass writes one row of stats about itself to the morph log, checks those stats against the tool's own requirements for improving, and prints what to improve next. Nothing about your code changes.

The standing tick. A fresh agent with no memory takes one item, measures the same stat before and after the change, and records whether it was worth it. Both ship in this kit, with the self-improving qualities we built for our ARC3 harness. Nothing starts a tick for you: TICK.md is its runbook, and you schedule it.

Turning it off

Run with --no-self-improve, or put self_improve: false in the model's loop: block. The pass then records no row and prints no picks. There may be some token saving, but on a pass it is small; the larger spend is the tick, which only runs if you schedule it, and stops when you stop scheduling it or create .loop_tick.STOP beside the tools.

The loop, in pseudo C++

The toolkit is written in Python. This is the same logic for a C++ reader; the lower-case names are the real ones in the code.

// One pass. Self-improvement is on by default.
Verdict run(Model& m, bool selfImprove = true) {
  Breaks  b = Mutate(m.code);       // one compile
  Results r = RunEachAlone(b, m.tests);
  Graph   g = KnowledgeGraph(m, r);
  Holes   h = Criteria(g);          // 17 checks

  if (self_improve_on(m, selfImprove)) {
    Row row = PassStats(m).collect();  // 44 stats
    MorphLog(m).add(row);
    auto fired = improvement::fires(rules, log);
    Print(NextImprovement(log, fired).picks());
  }

  return h.ours.empty() ? HOLDS : OPEN;
}

// One tick. A fresh agent, one item, no memory.
void Tick() {
  Start s = loop_tick::start();     // the lock
  if (s.stopped || s.busy || s.idle) return;
  if (s.epochStarts) Brainstorm();  // every 12
  RunSelftests();                   // red = item
  telemetry_audit();                // unread = item
  Item i = Choose(improvement::check(), board);
  Stat before = i.stat.Measure();
  i.Do();                           // one change
  Stat after = i.stat.Measure();
  if (s.epochEnds) {
    run_plan::decide();             // parts on or off
    improvement::graph();           // did it work?
  }
  loop_tick::finish(i, before, after, worth);
}

Three ticks in a row worth "no" and the tick sleeps until something it watches changes, so an idle loop costs almost nothing. The improvement graph is the same shape one level up: stats are its code, triggers its requirements, ticks its tests.

Telemetry: measuring growth both ways

A loop can look better by trying less, and look worse by trying more. So every number the loop records is one of five kinds, and they are read together:

Net
How hard the pass tried: how many breaks, how many kinds, how much code. Should grow, then hold.
Closure
How much of what it tried was caught, claimed or answered. Should grow towards the net.
Open
What is still open, and whose it is. Should shrink; the owner’s part only shrinks when the owner answers.
Cost
What a pass costs in time. Should not grow faster than the net.
Tool
The tool itself: its size, and how much of it its own planted mistakes prove.

A pass where the net grew and the open count grew too is progress, not a step back. The list of stats is revisited every pass, and a new one is added whenever a pass shows growth the existing ones miss.

How the stats choose what to improve next

Every pass, each stat in the morph log is read as a trend over the passes and given one word: improving, worsening, stalled (the last three values barely moved), done (an open count stuck at zero), or too few (fewer than three passes have it). The word compares the stat to the way its kind should move: the net and what was caught should rise, what is open should fall.

The next improvement is then chosen by the stats, not by a person’s feeling. Each area of the tool (tests, the GNN, the kinds of break, speed, the owner’s questions, assumptions, coverage) names the stats that speak for it. A worsening stat scores 3, a stalled one 2, and an area scores its worst stat. The GNN tune is also due every five passes. The pick, and the trend lines that chose it, are printed after every pass.

On against off

The loop’s own report cannot say whether the loop helps, because it grades work by its own rules. So there is a separate harness. One task goes to two agents, each in its own copy of the code. One works with the loop (the on arm), one without it (the off arm). Neither is told it is being compared.

  1. The task is a real prompt, taken from the team’s own past sessions.
  2. The harness measures what each arm produced. It never takes an arm’s word for it.
  3. A third agent grades both answers blind: it sees the task, the two changes labelled X and Y, and the measured results, and it does not know which arm is which.
  4. Every failure goes into one pile by kind (wrong behaviour, a missed requirement, an invented value, a weak test, and so on). “Different but both fine” has its own pile, so two good answers that differ are not counted as a failure.

A hidden acceptance test, written first

An arm’s own tests only show that it agrees with itself. So from the second pair on, the person setting up the pair writes an acceptance test before either arm starts. Neither arm ever sees it. It is copied into each arm’s copy only to be measured, then removed. The harness refuses to accept the test once either arm’s copy exists, refuses it if it changed after it was set, and proves beforehand that it can fail (on the code before the change) and can pass (on a reference change kept apart from both arms). The blind grader sees that test’s result, and not the arms’ own test counts.

What it can learn from its own stats

Every pass leaves a verdict for every break: which kind of break, on which statement, in which method, and whether a test caught it. That is training data. A small model trained on it ranks the breaks most likely to get past the tests first, so a pass can show its holes early, and an agent writing new code can be told where its tests are likely to be weak before anything runs.

The test that lets it improve

It is only scored on code it never saw: whole methods are held out, and the score is how many of the real survivors it finds in the first fifth of its ranking. Random order finds a fifth; the plain rule to beat ranks each kind of break by how often that kind survived before.

Planned rounds of improvement

The standing loop works in epochs of twelve ticks. The first tick of an epoch is a brainstorm: a fresh agent reads the stats, the tick log and the results, and ranks ideas by the one stat each should move. The last tick is a benchmark: the same fixed measures every time, on inputs no tick may change. An epoch counts as an improvement only if a number moved the right way and none moved the wrong way.

The code-writing side

Planned Connect what it learns to the agent that writes the code: before it writes tests, hand it the statements of its change most likely to get past them, and the requirement the GNN thinks its new method belongs to. Measured as a third arm beside on and off.

The loop on its own improvement

The loop records a great deal about itself: every pass leaves fifty numbers, and the learned parts leave evidence of when they help. Recording a number is only worth it if something reads it and acts. On 29 October an audit found 28 numbers that nothing read, and many more that were only printed.

So the improvement of the loop now has requirements of its own, written the way the product's are. Each number has a requirement saying what pattern in it should trigger something, what that is, and why the number is kept: a test that catches nothing for two passes is a speed item; an excuse for a harmless break that lapses is a hole; the graph not growing for three passes means the model is not being seeded. A number kept for a learner that does not exist yet must name that learner and a date. Past the date, unread, it fails.

Three levels, one graph

  • Level 1, the product. The loop holds the code to the product's requirements.
  • Level 2, the improvement. The loop holds itself to its improvement requirements, with the same kind of closure rules: every number covered, every trigger that fires acted on, every action naming the number it meant to move and its result measured, and an action that never moves its number retired.
  • Level 3 is level 2 again. How well the improvement graph is doing (numbers covered, triggers acted on, actions that worked) is itself written as numbers with requirements, so they sit in the same graph. The tower closes on itself.

The same learning applies one level up: once enough actions have measured results, a model can learn which kind of action moves which number, and it is switched on only where it beats the plain rule, like everything else.

How new is it?

An independent agent with web search compared the loop with published work on 29 October. Its answer: about eight of the ten parts are known. Requirements kept as data with gaps turned into questions are close to GitHub's Spec Kit and to Kiro's requirements turned into tests. Compiling all breaks at once and checking only what changed is what Stryker.NET already does. Breaks as feedback to an AI agent is Meta's mutation-guided test generation. Suggesting which requirement owns code is standard trace-link recovery.

Medium confidence What looks new is the whole used as an agent's "done" gate: every break in requirement-owned code must be caught by that requirement's own test, proven to change nothing by compiled code, explained with a reason that lapses when its code changes, or settled by the owner. Pieces of that exist (TestSuiteBench ties each break to one requirement and one test); the gate does not seem to.

It also said three things are aimed slightly off, and each could change the outcome more than polish: the breaks are syntactic while agents' mistakes are about intent; the on/off test graded correctness, where both sides hit the ceiling, rather than the tests left behind; and the GNN ignores its strongest signal, which requirement's tests catch the new code's breaks. The second is now measured (six kinds of task); the other two are on the work board.

The two targets

These are goals for the loop at its full potential, used where it fits. Neither has been measured yet.

95% accuracy or better

Target Agents using the loop on work it fits should get the task right at least 95 times in 100. The remaining 5% would be bugs in our own code.

How it will be measured: the on/off harness, graded blind, counted per failure pile, with the hidden acceptance test deciding whether the task was done.

Up to 90% fewer tokens

Target On average, up to 90% fewer tokens per closed requirement, because a later step looks up what the graph already holds instead of re-reading and re-deriving it. This number is always being re-evaluated.

How it will be measured: the same harness, from each arm’s own usage records (the tokens the model read and wrote), per task.

Measured The first data point goes the other way: on one small, precisely specified task, the loop used 58% more tokens for the same correctness (details). The target is about larger systems held across many changes, where re-reading and re-deriving is what costs; that has not been measured yet.

Other languages

The model, the graph, the checks, the GNN and the telemetry do not care what language the code is in. Only the part that breaks code does:

  • C#: any .NET project, through dotnet test.
  • Python: breaks code through its syntax tree; the tests are commands.
  • Anything else (C++, Blueprints): write an adapter that produces one result file in the same format the C# adapter writes: for each requirement, whether its code has the right shape, and for each break, whether a test caught it and which.

The harness matters more than the prompt

Most of the gain is in how the agents are set up, not in what they are asked. The loop is a harness: a model to act on, checks that can fail, a record that outlives the context window, fresh reviewers, and measurements of its own progress. Keep improving your own: the agents’ instructions, their tools, and what they must prove before they say “done”. Measure each change with the on/off harness rather than by feel.

What would help most in return:

  • Benchmarks: agents with and without it, on your own systems.
  • Failure piles: the kinds of failure you see, and how often.
  • A wrong pass: any check you can make pass for the wrong reason.
