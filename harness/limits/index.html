What it is not, yet

The first trial on code anyone can read

Measured The C# adapter was skipping code without saying so. On Unreal's own SemVer.cs it saw 35 of 68 statements, including none of the private method that does all the comparing, and on JsonObject.cs 213 of 288. It dropped overloaded methods, operators and generic methods with a where clause, and does not walk property bodies. The report still read as if the whole file was held. The shop feature has no overloads, which is why its numbers never showed it.

Open All fixed, each with a planted case: naming every overload and operator, a report that names what it did not walk, a read-only tree such as a Perforce workspace, a constructor of a nested type, one bad break stopping a whole run, and a break that hangs a test forever. A field's value and an indexer are still not walked, and the report says so. The shop feature's numbers barely moved: 96.5% of 1,097 is now 96.5% of 1,104, and 290 of 313 is now 294 of 317.

  • A prototype. Version 0.1. Its own model still names holes.
  • A thin model misleads. A green report over a small model reads as proof and is not (why).
  • Setup comes first. A problem story, requirements, use cases and tests a machine can run, before it helps at all.
  • Not a chatbot. It is a harness for agents that build systems. It does not answer questions.
  • It refutes, it never proves. “Closed” means closed against the breaks it tried (why).
  • Feel is not checked. Visuals, timing and feel still need a person to look.

Used where it does not fit, it can be worse than not using it at all.

The two targets

These are goals for the loop at its full potential, used where it fits. Neither has been measured yet.

95% accuracy or better

Target Agents using the loop on work it fits should get the task right at least 95 times in 100. The remaining 5% would be bugs in our own code.

How it will be measured: the on/off harness, graded blind, counted per failure pile, with the hidden acceptance test deciding whether the task was done.

Up to 90% fewer tokens

Target On average, up to 90% fewer tokens per closed requirement, because a later step looks up what the graph already holds instead of re-reading and re-deriving it. This number is always being re-evaluated.

How it will be measured: the same harness, from each arm’s own usage records (the tokens the model read and wrote), per task.

Measured The first data point goes the other way: on one small, precisely specified task, the loop used 58% more tokens for the same correctness (details). The target is about larger systems held across many changes, where re-reading and re-deriving is what costs; that has not been measured yet.
