On against off

The loop’s own report cannot say whether the loop helps, because it grades work by its own rules. So there is a separate harness. One task goes to two agents, each in its own copy of the code. One works with the loop (the on arm), one without it (the off arm). Neither is told it is being compared.

  1. The task is a real prompt, taken from the team’s own past sessions.
  2. The harness measures what each arm produced. It never takes an arm’s word for it.
  3. A third agent grades both answers blind: it sees the task, the two changes labelled X and Y, and the measured results, and it does not know which arm is which.
  4. Every failure goes into one pile by kind (wrong behaviour, a missed requirement, an invented value, a weak test, and so on). “Different but both fine” has its own pile, so two good answers that differ are not counted as a failure.

A hidden acceptance test, written first

An arm’s own tests only show that it agrees with itself. So from the second pair on, the person setting up the pair writes an acceptance test before either arm starts. Neither arm ever sees it. It is copied into each arm’s copy only to be measured, then removed. The harness refuses to accept the test once either arm’s copy exists, refuses it if it changed after it was set, and proves beforehand that it can fail (on the code before the change) and can pass (on a reference change kept apart from both arms). The blind grader sees that test’s result, and not the arms’ own test counts.

What happened so far

Measured The first pair: both arms passed their own tests. The on arm hit a crash in the loop itself (it failed when the code and the copy sat on different drives). That crash is fixed, and the pair counts as “tool failed”, neither for nor against the loop.

Measured The second pair, the first fair one (a small task: say what unlocks a line that is not on sale yet). The hidden test was proven first: it fails on the code before the change, on two wrong answers that compile, and passes on a reference answer kept apart from both arms.

  • Correctness: a tie. Both answers pass the hidden test 5 of 5 and their own 49 tests, and both mark the new wording as an open question for the owner.
  • Cost: the loop cost more. With the loop: 337,580 tokens and 39 minutes. Without it: 214,293 tokens and 6.5 minutes. That is 58% more tokens on this task, not fewer.
  • The blind grader preferred the answer made without the loop, because it stayed inside the task. The loop arm’s one failure was scope creep: following the loop’s report, it fixed listed items its change had not caused.

One pair is one data point, on the kind of task this manual says the loop is not for: small and precisely specified. It still showed two things to fix. The arm started in a model with hundreds of old holes it had not caused, and the report did not separate the holes its change made from those already there. Both are on the board.

The off arm still follows the project’s own working rules (never guess a value, say what was not verified), so the comparison measures the tool, not discipline.

Six kinds of task, on against off

One pair says little, so on 29 October six small tasks of different kinds were each given to two agents, one with the loop and one without. Each task has a hidden acceptance test, written before either agent started and proven first: it passes a reference solution and fails the untouched code. Beside it sits a second score, after the novelty review below: the tests each answer leaves behind are run against plausible wrong versions of the feature (a refund that forgets the stock, a menu that wraps only one way), and the score is how many of those wrong versions they catch. Each wrong version was itself checked to fail the hidden test first.

Where these numbers come from

Measured A refund (C#, precise): both passed the hidden test 7 of 7, and both left tests that catch 9 of 9 wrong versions. With the loop: 203,945 tokens and 14.5 minutes; without: 128,015 and 5.1. The blind grader preferred the answer made without the loop, which also guarded a stock count against overflow.

Measured A bulk purchase (Python, precise): both 9 of 9 on the hidden test and 9 of 9 wrong versions caught. With the loop: 237,213 tokens and 9.4 minutes; without: 128,011 and 3.2. The grader preferred the loop answer, on a point that favours the loop's own habits (it declared a harmless break the way the model already does).

Measured "Make buying fairer" (vague): without the loop the agent changed nothing and asked the owner four questions; with it, the agent added a "how much you are short" helper and a forgiveness amount that starts at zero, and wrote the amount down as the owner's question. Both pass the hidden test, which holds only the rules already stated. 214,714 tokens and 15 minutes against 103,391 and a minute. The grader preferred the loop answer; the other agent's questions were only in its reply, which the grader never sees.

Measured Owners for 13 unowned branches (the model only): both gave every method an owner. With the loop: 309,133 tokens and 47 minutes, closing 14 holes and opening one it could not close; without: 251,751 and 8 minutes. Both pass the corrected hidden test 12 of 12 (the first version of that test had two flaws of its own, both reported).

Measured A menu that wraps (Unity, a requirement an existing test contradicts): both 7 of 7. With the loop: 352,912 tokens and 77 minutes; without: 189,555 and 7. The grader preferred the loop answer: the other quietly changed an edge case the task said to keep.

Measured A bug in the tool itself: both 8 of 8. With the loop: 297,545 tokens and 145 minutes (two full passes over the tool's own code); without: 127,704 and under 3. The grader preferred the loop answer, whose tests pinned more of the behaviour. Along the way the loop arm found four real bugs in the tool, all since fixed.

The six, by their first blind grader: the loop answer was preferred 4 times, the answer without it twice. Every answer passed its hidden test either way.

The same tasks again, and three graders on each

On 30 October five of the six were repeated with the same hidden tests and the tools as they then stood. The sixth, the bug in the tool itself, could not be repeated because that bug is now fixed. One grader per pair turned out to be too noisy, so two more blind graders then judged every pair, each with its own coin for which answer is X, on briefs with the arm's tells removed.

Where these numbers come from

Measured By the majority of three graders: the loop preferred on 7 of 11 pairs, the answer without it on 3, 1 split. Round 1: loop 5, without 1. Round 2: loop 2, without 2, 1 split. All three graders agreed on 7 of the 11.

Measured What one grader would have told you. With only the first grader, rounds 1 and 2 together came to 5, 5 and 1, and 3 of the 5 repeated tasks reversed. With three graders, 1 reversed (the fairer rule) and 1 went to a split (the wrapping menu). The noise was the single grader.

Measured The losses are consistent. The model-only task went against the loop 3 to 0 in both rounds. On the fairer rule's repeat, 3 to 0 against: the loop arm removed a public constructor, so the hidden test no longer compiled, while the loop reported that everything held. The loop does not yet hold the public surface of the code (a planned check).

Measured What the 28 newer grades counted (6 of them compare the loop to the hint arm below): left unfinished, 9 with the loop and 18 without; scope creep, 4 and 10; invented values, 17 and 5. The loop writes more down, and graders call some of that invented.

Measured Two first grades are weaker than the rest. Three loop arms of the 27 read the run's own notes, which can say how the other arm finished, and two diffs named the arm or the tool. Those tells are now blanked for graders and each arm can be scanned for what it read. The first grade of each pair is still on the older brief.

A cheap hint instead of the loop

A third kind of arm got no loop at all, only a short list before writing its tests: the statements of the code it changed most likely to let a break past the tests, learned from the project's own past results.

Where these numbers come from

Measured Three tasks against the loop arm. Every answer passed its hidden test. Tests left behind were equal on all three (9 of 9, 9 of 9, 7 of 8). The bulk purchase tied. On the refund and the wrapping menu the grader preferred the loop answer, but the code behaved the same and the edge was in what it wrote down, such as recording the new rule as a requirement. The loop arm cost 1.7 to 2.3 times the tokens and 3 to 10 times the minutes of the hint arm.

Growing a model from a small seed

What looked like the largest gap went away once the run was fair. An agent was given a feature's problem story, its sources and its 3 most cross-cutting requirements, and asked to grow the rest of the model; another did the same without the loop. Each was scored by how many of the real model's other requirements it arrived at, matched by the methods they own, never by wording.

Where these numbers come from

Measured With the requirement ids removed from the code: 16 of 24 each, a tie. Of the requirements each grew, 14 of 46 matched a real one with the loop and 12 of 41 without. With the loop: 511,317 tokens and 81 minutes; without: 323,773 and 17. One run each, and neither arm asked for anything it should not see.

Measured The first run read 19 of 24 against 10, at 515,241 tokens and 68 minutes against 277,720 and 13, but the code cited its requirement ids, so both arms started with more than the 3. Do not quote it. Recovering a model is not where the loop has shown a gain.

What it says so far. On small tasks correctness does not separate the two: nearly every answer passed its hidden test, and the tests left behind were as strong either way where they could be compared. Graders still prefer the loop's answers more often than not, mostly for what they leave finished and written down. The loop cost 1.2 to 2.3 times the tokens and 3 to 55 times the time. Where it does differ is in what gets written down: the open questions, the new requirement, the reason a claim changed. That fits when it fits: the loop is meant to pay over many changes, and that has not been measured yet. Inside one small change it does not, and the one fair test of building a model tied.

The harness was tested too. Five of its own faults turned up and were fixed: hiding a chain's file name blanked a plain word in one answer and voided a grade; the grader was told the requirements were those of one feature for every task; one hidden test was stricter than its task; answers given only in a reply are invisible to the grader; and the loop brief told a model-only task to write tests.

The first round's two losses still say something, whichever way the repeats went. On the refund the answer without the loop guarded an overflow the loop answer missed. On the model-only task the loop answer closed its holes by pinning code on requirements whose words do not cover it: the count of holes reached zero without the intent being met. That is now a planned check (a second opinion on every claim).
